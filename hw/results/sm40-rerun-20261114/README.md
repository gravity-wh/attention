# SMIC40 九角重跑（2026-11-14 23:16–23:41）

> 一句话：把整棵树同步到 `a0e713a` 之后，用**会实测装载拍数**的新 `tb_attn.sv`
> 把三方案 × 三个角（tt/ss/ff）全部重跑了一遍。九行数据的 `ld` 从此是实测 768，不是脚本补的。

## 1. 为什么要重跑

`05-SMIC40综合结果.md` §5 的口径是「`cycles` = `start`→`done` + 装载」，
而装载拍数由 `tb_attn.sv` 的 `drive_load()` 自己数、在 `[SUMMARY]` 行尾以 `ld=` 上报
（commit `9135df8`）。但 11-14 22:03 那次 varB 全量回归是在**没有同步过的 VM 副本**上跑的：

| 文件 | VM 上那份（22:03 用的） | 仓库里那份（本次用的） |
|---|---|---|
| `tb/sys/tb_attn.sv` | 17,616 B，`drive_load()` 无返回值、`[SUMMARY]` 无 `ld=` | 18,491 B，返回装载拍数并上报 `ld=` |
| `flow/collect/collect.py` | 旧版，`cycles = lat_max + 768` 硬编码 | 新版，`cycles = lat_max + ld` |
| `flow/sim/run.sh` | 旧版，`summary.csv` 只有 13 列 | 新版，第 14 列写 `ld` |

结论：那次 `lat 1423` 是真的，但端到端 2,191 里的 768 是**脚本补的**，不是 tb 数的。
本次把整棵树（`tar` 覆盖 `hw/`，保留 `runs/`）推上去后重跑，`ld` 由 tb 直接给出。

## 2. 怎么跑的

驱动脚本就放在本目录，原样可复跑：

```bash
bash run_full.sh      # vec(full) → ref/varA/varB 各 make pair MODE=full
bash run_corners.sh   # ss/ff 六个角补仿真半边（varB 两角连综合一起重做）
```

- 机器：CentOS 7.9 VM，8 vCPU / 15 GB，VCS V-2023.12-SP2，Genus 15.20-p004_1
- PDK：SC9MC 40LL，`PDK=SC9MC`
- 种子：`20260101`，`MODE=full`（random/zero/extreme/cancel 各 200/4/200/200，reset 4，cont 8）
- 时间线：22:46 起跑 → 23:16 三个 tt 全量 + 综合完成 → 23:41 ss/ff 六个角补齐
- 旧目录：`runs/*-sm40-tt` 先移到 `runs/_archive/`，避免 `summary.csv` 追加出重复行

九行全部 `PASS`，`mism = 0`，`ld` 恒为 768，`cycles_calc` 与改动前逐值相同：

四个观察：

1. **D₀/D 在三个角上是同一个数**（2.88 / 4.76）。周期数只与 RTL 调度有关，与角无关 ——
   这本身就是"周期数来自仿真、面积功耗来自综合"这两条腿没串味的证据。
2. **面积/功耗与改动前的记录逐位相同**（varB tt 73,296.9 / 16.096，ss 83,004.8 / 14.806）。
   Genus 单角综合是确定性的，重跑不产生漂移，所以 `613ec89` 的 ss/ff 综合结果可以直接复用。
3. **数值精度一点没动**：ref 的 RMSE 0.000187 / max|e| 0.000590，varA、varB 的 0.002492 / 0.006034，
   与 1,738 拍版本逐字段相同 —— 早释放只改调度，不改数据通路。
4. **`cancel` 类仍是 1,375 / 1,399 / 1,423 三档**，原因是跳零组的既有特性（原实现同样如此），
   不是本轮改动引入。

## 5. 这一轮没做的事

- **GPDK045 那六行没有重跑**：`ref/varA/varB` 的 `-base`/`-opt` 是 45nm 的历史记录，
  它们的 `summary.csv` 没有 `ld` 列，`cycles` 因此等于 `cycles_calc`。
  不同工艺的绝对值本来就不能直接比，`make table TABLE_PDK=SC9MC` 会把它们过滤掉。
- **门级仿真与 P&R 未动**：本轮只到综合。`07-后端PR结果.md` 仍是旧网表的记录。
