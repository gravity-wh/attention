01题目要求：到底在考什么

把 9 页题面拆成三条互不重叠的约束：数值上必须对，结构上必须比，口径上必须同。

题面写得很短，但真正的难点不在“实现一个注意力模块”——16×16 的矩阵乘法，一个本科生两天就能写出来。 难点在于它同时提出了三个方向相反的要求：

① 数值上必须「对」

输出要与 float64 参考的 RMSE ≤ 0.06、单元素误差 ≤ 0.20， 同时还要与自己那份软件模型逐位一致。前者管“算得准”，后者管“算得和你说的一样”。

② 结构上必须「比」

至少两套方案 + 一组单变量对照。而 40 分的效率项不是绝对指标， 是相对于统一参考实现的改善倍数——所以必须有一把“没优化过”的尺子。

③ 口径上必须「同」

同工艺、同工具、同角、同电压温度、同驱动负载、同评测规则。 这句话决定了整个工程的组织方式：三套实现必须能被同一份 tb 驱动。

由此得到的第一条设计原则

不要把三套实现写成三份代码。接口共享 → 数据通路尽量共享 → 只有编排逻辑各占一坑。 这样“其余条件一致”不是靠人守着，而是结构上不可能不一致。

02总体技术路线

六层：题面约束 → 数值契约 → RTL 三方案 → 验证 → 综合 → 报告。每层只对下一层负责。

整条链路的组织原则是单向依赖、逐层收口：上一层的产物是下一层的唯一输入，任何一层都不许 “顺手”改变上一层的决定。这条纪律换来的是可复现性——报告里每个数字都能指回一个文件、一个 commit、一次运行。

顺序铁律

先模型、后 RTL。 attn_model.c 里的 attn_fixed() 是逐位模型， 它同时是 RTL 的规格书和比对对象。RTL 写不通时正确的动作是先改模型（因为它更容易改对）， RTL 只是把已经跑通的模型翻译成硬件。“模型和 RTL 各错一半、碰巧对上”是这项最容易踩的坑。

03方案选取：三套实现 + 一条数值主线

ref 提供分母，varA 隔离并行度，varB 隔离数据流形态；三者共享数值格式与数据通路。

题面要求“实现并比较至少两个设计方案”，并且效率分建立在“相对统一参考实现的改善”上。 这句话把方案设计变成了一个正交分解问题：如果要报三个相对改善倍数，就必须清楚每个方案 相对基准动了哪一个变量，否则改善归因不清，20 分的理论分析也写不实。

为什么 varA 与 varB 用同一套数值格式

如果两套方案的位宽不同，A 与 B 的差异里就同时混进了“结构”和“精度”两个变量， 对照实验立刻失效。数值格式固定为 qb10/qf7，只在结构上做文章； ref→varA 的差值是“不做优化 vs 做优化”的总账，这正是 40 分要报的那笔账。

数据流形态

参考实现这条“尺子”怎么来的

题面的说法是“每题使用统一固定的参考实现，学生将其适配到自选工艺”。我们拿不到那份实现时， 做法是自己写一个结构最朴素的版本，并把它冻住——它的价值不在性能，而在“未优化的定义”。

  • 结构朴素到底：一条 16 深 MAC、逐元素串行、没有并行、没有流水线重排。
  • 数值贴近题面：qb16/qf13，几乎是 FP16 的定点等价物，代表“没做量化优化”的基线。
  • 三条可借的近似：LUT 化 exp、每行一次倒数、P·V 的零元素门控。这三条来自 reference/ 里两篇 ISSCC 论文，但它们属于“算法层近似”，与结构优化正交， 所以 ref 里也允许出现——这样 ref→varA 的差值才干净地只反映结构。
明确不借的部分

论文里的 BESA 近位宽乘法器（小值走近似、大值精确）在这里用不了。 “与自身软件模型逐位一致”意味着乘法一旦近似，累加结果就漂，逐位比对必然挂。 近似只能出现在模型已经规定近似的地方（exp / 倒数 / 量化），MAC 必须精确。 这不是保守，是判据决定的。

04数值契约：位宽是怎么定下来的

题面只给两条误差上限，位宽是自己推出来的——推导过程就是 20 分理论分析的主体。

定点方案里最容易犯的错是“拍一个位宽，跑一遍看误差，不够就加两位”。这样做出来的数字没法解释， 也没法回答“为什么不用 8 bit”。我们的做法是先建误差模型，再用扫描验证模型，两者对上才选工作点。

误差预算：为什么 Softmax 必须比输出精度高

误差沿数据流只有一条需要小心：

# 量化 → 点积 → 指数 → 加权求和，每一段的放大关系
δ(Q,K) ──量化──▶ δS ──exp 的指数敏感──▶ δp/p ≈ δS ──加权求和──▶ δY

关键在于 δp/p ≈ δS（以 nat 为单位）：Softmax 对 S 的绝对误差极其敏感， 因为 exp 把加性误差直接变成乘性误差。这决定了 S 的定点分辨率必须远高于 Y 的分辨率—— 所以 S 和 p 都取 F=16，而最终输出中间值只需要 F=13。

位宽扫描：把“为什么不是 8 bit”画出来

固定 qb=16（避免饱和干扰），只扫小数位 qf，每类 200 帧取最大单帧误差。 曲线在 qf ≤ 9 段严格随位宽 2 倍下降（自洽），qf ≥ 10 段压到 FP16 输出舍入的地板。

安全系数：随机相位假设不总成立

上图的数字是“随机相位”假设下的。但存在一类合法输入会让误差相干叠加：若 K 的各行近似平行 （同一符号向量、仅整行幅度不同），16 个乘积的量化误差会同号累加，而不是按 √16 平均。 实测这种退化输入下误差放大 3～5 倍。按 5 倍预留后：8 bit → 0.098（超限）， 10 bit → 0.020（3 倍余量），12 bit → 0.0045（13 倍余量）。 这就是排除 8 bit 的真实理由——不是标称超标，而是安全垫不够厚。

三个关键取舍

① 为什么 QF = QB − 3：把范围做到 ±4 而不是刚好 ±2

题面允许输入 [−2, 2]。若把范围压到刚好 ±2，10 bit 就得用 QF=8，此时 +2.0 恰好落在 2⁹−1 与 2⁹ 的交界上，会饱和；而“规定范围的正负极值”正是六类必测向量之一，专门打饱和。 留 1 bit 幅度余量后范围是 ±4，代价是有效位数少约 1.3 bit，收益是任何合法输入永不饱和。

这个取舍是可量化的：8 bit + QF=6 能多 1 bit 分辨率，但 +2.0 会削到 1.9844 （误差 1.6e−2）。在极值用例里这是系统性偏差；而少 1 bit 分辨率只是均匀白噪声， 会被 Softmax 归一化部分吸收。选留余量。

② 为什么 Softmax 走 2 的幂分解，而不是查 exp 大表

要算 e^(−d)，d ∈ [0, 32]。直接建表要覆盖 32 个 nat 的宽度：按 2⁻⁷ 步长 → 4096 项（不可接受）； 按 2⁻³ 步长 → 256 项，但 e 的曲率在整个区间变化剧烈，插值误差仍然大。改成 2 的底：

e^(−d) = 2^(−d·log₂e) = 2^(−n−f) = 2^(−n) · 2^(−f),   n ∈ ℤ≥0, f ∈ [0,1)
  • n 的部分是一次桶形移位，零成本；
  • f 的部分只需覆盖 [0,1) 一个区间，2⁻¹ 在该区间内曲率温和，16 项 + 线性插值就够。

实测 16 项 LUT 的插值最大相对误差 6.9e−5，远小于量化误差，等于白送。 另外 n ≥ 16 直接置 0：此时 2⁻¹⁶ 已低于 p 的一个 LSB，置零不损失可表示信息， 还省掉移位器位宽——这同时保证 d 再大也不会溢出，所以 exp 里不需要饱和保护。

③ 为什么归一化用「一次倒数 + 16 次乘法」

朴素做法是 p_i = e_i / T，每行 16 次除法。改成 R = round(2⁴⁰ / T)（每行 1 次），再 p_i = (e_i·R + 2²³) ≫ 24： 除法器从 16 个降到 1 个，其余是乘法器（本来就有）。2⁴⁰ 的分子保证 R 的相对误差 < 5e−7， 对 16 位精度的 p 完全无感。实测每行 Σp 相对 65536 的偏差 ≤ 5 LSB。

刻意不做的优化

整套流水线只有三次尺度转换，全部是 2 的幂或常量乘，没有 per-tensor / per-row 动态缩放。 理由：输入被题面限定在 [−2, 2]，动态范围是已知常数，动态缩放省不出位宽，反而引入额外控制与精度损失。 这一条要写进报告的“自主设计”里——它是主动放弃，不是遗漏。

向量契约：为什么必须由 C 模型导出

“逐位一致的软件模型”和“测试向量”必须出自同一份代码。只要多一条重新实现的路径， 就多一个不一致的来源——而那正是这项要被扣分的地方。所以 dumpvec 直接调 attn_fixed() 导出期望值，不另写 Python 重算一遍。

 以上为 ref 方案（qb16/qf13，seed 20260101，每类 2 个任务）的实测结果，共 12 任务、0 失配。 varA / varB 待 RTL 完成后按同一套向量重跑。
覆盖率：能采，但出不了 urg 报告

vcs -cm line+cond+fsm+tgl+branch 编译通过、simv 也能产生 simv.vdb，但 urg -dir simv.vdb 崩在 covdb_get_license()—— 这台机器的 license 不含 URG 特性。所以 build.sh 默认不开 -cm（采了也没法出报告，只拖慢仿真）。 报告里的证据链改为：六类回归表（每类一行 + 状态）＋ runs/<TAG>/sim_<cat>.log。 题面要的是“六类激励都覆盖到”，不是行覆盖率百分比——这样反而更贴题，也不依赖 license。

06PDK 与综合环境

45 nm 通用库 + Genus 15.2，三个角齐全；两个必须知道的坑都写进了流程的自动检查。

题面允许 SKY130、GF180MCU 或学校可用的其他工艺。我们选了 VM 上工具自带的两套 45 nm 库之一， 理由是角和工具链都在同一台机器上、且已被脚本验证过——40 分的效率项依赖“成对测量”， 换工艺的迁移成本会直接吃掉可用的迭代次数。

坑一 · 库里的面积全是 0.0

演示库被剥掉了面积字段，Genus 读库时会刷一屏 Warning : Libcell has no area attribute. Defaulting to 0 area. [LBR-43]。 只读 .lib 的话 report_area 给出 0 µm²——而 0 会一路混进报告表 2， 表现为“面积改善了无穷倍”。面积的真实来源是 LEF（gsclib045.lef 里 487 个 MACRO 都有 SIZE W BY 1.71）。所以流程强制 read_physical -lef， 并在解析后体检：面积解析不出来或等于 0 就直接失败退出，不允许生成一个“看起来跑完了”的 0 面积结果。

坑二 · 电压不是 0.9 V

题面模板里的 tt_25C_0.90V 只是个占位符。实测这个库的典型角是 1.20 V。 动态功耗 ∝ V²，按 0.9 V 去报而库是 1.2 V，功耗数字整体会差约 78%。 variants.mk 里原来的占位符已经改掉，现在 PVT 标签只从 pdk.mk 派生。

三个数字的统计边界

报告里每个数字后面都要能接上这句边界说明。这是“报告与复现”那 10 分的实际内容， 也是被追问时唯一能站住的部分。

指标怎么来的边界（写进报告）
面积 A (µm²)report_area 的 Total area，单元面积取自 LEF综合后网表的标准单元面积；不含布线开销、不含时钟树、不含 IO/pad、不含 SRAM 宏（本设计未用宏）
时延 D (µs)仿真测得的 lat_max（周期数）÷ 频率 (MHz)从 start 到最后一个 o_vld 输出，含格式转换、运算、存储、控制全流程；不是单条路径延迟
功率 P (mW)report_power，活动率固定 toggle 0.1 / static 0.5静态估计，不是仿真功耗（没有 VCD 反标）；绝对值仅供同条件比较
能耗 E (nJ)P (mW) × D (µs)量纲正好是 nJ；这是“一次完整任务”的能耗，不是峰值功耗
频率 (MHz)综合时的时钟约束目标值不等于可达频率，见下
 面积 / 时序 / 功耗三项必须在同一次 syn_map/syn_opt 之后取： VM 上没有 PrimeTime / PowerArtist，好处是三者天然自洽（同一份网表），代价是没有独立的 sign-off 工具复核。 报告里必须写明这个口径，不能把综合估计说成签核结果。

频率怎么报：目标频率 ≠ 可达频率

题面要填“运行频率”和“完整任务周期数”，而周期数乘频率才是时延。如果频率随便填一个好看的数， 时延和能耗就全是假的。所以分两步：先在统一的标称频率下综合，拿到 WNS；再由 slack 反推可达频率 f_max ≈ 1/(T − WNS)。这是综合估计，不含布线寄生。

WNS含义怎么做
> 0目标频率有富余直接用目标频率报，同时报 f_max 说明天花板在哪
≈ 0正好卡住最理想——说明频率是“设计出来的”而不是“捡来的”
< 0目标频率达不到不能直接报目标频率：要么降频到 f_max 重跑，要么先修关键路径
 表 2 的“频率”一列最稳妥的填法：实际综合所用频率 ＋ 该频率下的 WNS， 脚注写 f_max ≈ xxx MHz（综合估计）。这样无论怎么追问都有据可查。

① hw/ 与 docs/ 分开

hw/ 里只放能被工具直接消费的东西：源码、脚本、约束、可复现的指标。 docs/ 里只放叙述与图。任何“代码里的魔法数字”必须在 docs/ 能查到出处； 任何“报告里的数字”必须能顺着 TAG 追回 hw/runs/。

② runs/ 与 results/ 分开

runs 是现场（乱、大、可丢），results 是结论（小、干净、必须进库）。 把这两者混在一起，两周后你无法回答“这个数字是哪次跑出来的”。

 规则：任何流程改动都先进 flow/ 再进 Makefile，不许手敲工具命令—— 手敲的命令没法复现，而“复现”是 10 分。

三条设计上的护城河值得单独说，因为每一条都对应一次踩过的坑：

  • 数值格式只有一个真源。 config/variants.mk 的三行（qb/qf/lut）同时决定 三处：C 模型导出哪个黄金值、RTL 编译时的 Q_BITS/Q_FRAC、tb 读哪个 exp 文件。 三者同源，才不会出现“向量按 16 bit 生成、RTL 按 10 bit 综合”。
  • 端口契约用宏，不用 SV interface。 interface 在 Genus 上要额外开关才综合，而宏头文件在所有工具上都通行。 这是“本地能验”和“服务器能综合”的交集。
  • 三条方案目录并行，不用分支。 分支切来切去没法同时综合、同时对比，公共 bug 修复要 rebase 三次， 忘记同步一次对比就失真。分支区分“做完了没”，目录区分“是哪个方案”。

一句话总结这套方案的赌注

我们把分数押在“数值上做深、结构上做对比”，而不是“堆一个很花的加速器”。 理由是：16×16 的规模根本吃不满任何阵列，真正能拉开差距的是位宽（面积 ∝ QB²）和 Softmax 的实现方式（一次倒数、LUT 化 exp）。前者已有 15 倍精度余量作保， 后者有可综合的 RTL 作证——这两条在答辩时都能落到具体电路上，而不是停在架构框图。
