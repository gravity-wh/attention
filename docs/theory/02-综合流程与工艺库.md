# 综合流程与工艺库选择

> 这份文档回答四个问题：**用什么库、约束怎么定、三个数字的统计边界在哪、频率怎么报。**
> 40 分的综合效率项全部建立在"成对测量、条件一致"上，这一份就是那套条件的说明书。
> 配置的唯一真源是 `hw/config/pdk.mk`，本文只解释"为什么"。

---

## 1. 环境与库：实测结论

### 1.1 工具

| 环节 | 工具 | 说明 |
|---|---|---|
| 综合 | **Cadence Genus 15.20-p004_1** | `/opt/cadence/GENUS152`，VM 上已验证可跑 |
| 时序 | 同上（Genus 内置 STA） | **没有 PrimeTime**，所以不另起一步做 sign-off STA |
| 功耗 | 同上（`set_switching_activity` + `report_power`） | **没有 PowerArtist/PrimePower**，功耗只能在综合里出 |
| 仿真 | Synopsys VCS V-2023.12-SP2 | 见 `hw/README.md` 第五节 |

**由此决定的一件事**：面积、时序、功耗三项必须在**同一次** `syn_map/syn_opt` 之后取。
好处是三者天然自洽（同一份网表）；代价是没有独立的 sign-off 工具复核。
报告里要写清这个口径，不能把综合估计说成签核结果。

### 1.2 可选库：只有两套 45nm

VM 里工具自带两套标准单元库，单元名完全相同（同一套单元的两次表征）：

| 库 | 路径 | 工艺角 | 单元数 | 面积字段 |
|---|---|---|---|---|
| **GPDK045** | `$INNOVUS/share/FoundationFlows/EXAMPLES/INNOVUS/DESIGN/GPDK/LIBS/GPDK045` | **tt / ff / ss 三角齐全** | 477 | **全为 0.0** |
| gsclib045_v3.5 | `$CONFRML/share/cfm/lec/demo/rcv_intro/libs/gsclib045_v3.5` | 只有 slow | 486 | **全为 0.0** |

选 **GPDK045**：三个角齐全，报告里的"工艺角"一栏才有内容可写（`make synall` 一次跑完）。

### 1.3 两个必须知道的坑

**坑一：`.lib` 里所有单元面积都是 0.0。**

Genus 读库时会刷一屏 `Warning : Libcell has no area attribute. Defaulting to 0 area. [LBR-43]`。
只读 `.lib` 的话 `report_area` 给出 0 µm² —— 而 0 会一路混进报告表 2，表现为"面积改善了无穷倍"。

面积的真实来源是 **LEF**：`gsclib045.lef` 里 487 个 MACRO 都有 `SIZE W BY 1.71`。
所以流程强制：

```tcl
read_libs $lib
read_physical -lef $lef      # ← 没有这一步，面积全 0
```

并且 `run_syn.sh` 在解析完之后有一道体检：面积解析不出来或等于 0 就**直接失败退出**，
不允许生成一个"看起来跑完了"的 0 面积结果。

**坑二：电压不是 0.9 V。**

`config/variants.mk` 里原来写着 `PVT ?= tt_25C_0.90V`，那是照抄题面模板的占位符。
实测三个角的真实参数：

| 角 | 库文件 | process | voltage | temperature | PVT 标签 |
|---|---|---|---|---|---|
| 典型 | `typical.lib` | 1.0 | **1.20 V** | 25 °C | `TT_25C_1V20` |
| 快 | `fast.lib` | 1.0 | **1.32 V** | 0 °C | `FF_0C_1V32` |
| 慢 | `slow.lib` | 1.0 | **1.08 V** | 125 °C | `SS_125C_1V08` |

动态功耗 ∝ V²，按 0.9 V 去报而库是 1.2 V，功耗数字整体会差约 **78%**。
现在 PVT 标签由 `CORNER` 从 `pdk.mk` 派生，**标签与实际加载的库文件必然一致**——
这是把"写错标签"变成不可能，而不是靠人记得改两处。

## 2. 约束怎么定，为什么这么定

全部写在 `config/pdk.mk`，`run_syn.sh` 据此生成 SDC。**任何一项改了都必须重跑综合并重新记录。**

| 约束 | 取值 | 为什么是这个值 | 影响 |
|---|---|---|---|
| 时钟 | `clk`，周期 = 1000/CLOCK ns | 频率是变量，`CLOCK` 来自 `variants.mk` | 决定时序与功耗 |
| 时钟不确定性 | 5% 周期 | 综合阶段没有时钟树，用固定比例吸收 jitter + 偏斜 | 吃掉一点时序余量 |
| 输入驱动单元 | `BUFX4` | **不用 ideal 驱动**。ideal 驱动给 0 输入转换时间，路径延迟偏乐观，而且会把三个方案之间的差异抹平 | 输入路径延迟 |
| 输入转换时间 | 0.05 ns | 与 `BUFX4` 驱动量级匹配 | —— |
| 输出负载 | 0.016 pF | 约等于一个扇出 2 的门 + 一小段线；综合阶段无布线信息，只能声明+固定 | 输出路径延迟 |
| I/O 延迟 | 各 25% 周期 | 粗略反映"外面还有一级寄存器"，留一半周期给组合逻辑 | 端到端时序 |
| `rst_n` | `set_false_path` | 异步复位，不做时序检查，否则会被当成跨时钟路径 | —— |
| 活动率 | toggle 0.1 / static 0.5 | 功耗必须建立在明确假设上，否则两次的 mW 不可比。0.1 = 数据类信号平均每 10 拍翻一次 | **直接决定 P 与 E** |
| 时钟门控 | 显式禁止（15.2 无此属性则事后检查） | 三个方案若一个插了 ICG、一个没插，面积差里就混进了与算法无关的变量 | 事后用 `get_cells *ICG*` 计数确认 |

> **不可协商的一点**：以上所有项在 ref / varA / varB 之间必须逐字相同。
> 它们不是"调参"，是实验条件。调了就不是对照实验。

## 3. 三个数字的统计边界

报告里每个数字后面都要能接上这句话。

| 指标 | 怎么来的 | 边界（写进报告） |
|---|---|---|
| **面积 A (µm²)** | `report_area` 的 Total area，单元面积取自 LEF | 综合后网表的**标准单元面积**。不含布线开销、不含时钟树、不含 IO/pad、不含 SRAM 宏（本设计未用宏） |
| **时延 D (µs)** | 仿真测得的 `lat_max`（周期数） ÷ 频率 (MHz) | 从 `start` 到最后一个 `o_vld` 输出，含装载后的运算全流程。不是单条路径延迟 |
| **功率 P (mW)** | `report_power`，活动率固定为 toggle 0.1 / static 0.5 | **静态估计**，不是仿真功耗（没有 VCD 反标）。绝对值仅供同条件比较 |
| **能耗 E (nJ)** | `P (mW) × D (µs)` | 量纲正好是 nJ（1 mW × 1 µs = 1 nJ）。这是"一次完整任务"的能耗，不是峰值功耗 |
| **频率 (MHz)** | 综合时的时钟约束目标值 | 不等于可达频率，见 §4 |

## 4. 频率怎么报：目标频率 ≠ 可达频率

题目要求填"运行频率"和"完整任务周期数"，而周期数与频率相乘才是时延。
如果频率随便填一个好看的数，时延和能耗就全是假的。所以分两步：

**第一步：在统一的标称频率下综合。** `clock_ref = 100 MHz`、`clock_varA/varB = 200 MHz`
（见 `config/variants.mk`），三个方案各自综合，得到 WNS。

**第二步：由 slack 反推可达频率。**

```
f_max ≈ 1 / (T − WNS)        T = 1000 / f_target
```

`parse_syn.py` 已经把 `fmax_mhz` 算好写进 `metrics.csv`。注意这是**综合估计**：
不含布线寄生，真实 f_max 要等 P&R，报告里必须写"综合估计"。

三种情况的处理：

| WNS | 含义 | 怎么做 |
|---|---|---|
| > 0 | 目标频率有富余 | 可以直接用目标频率报；同时报 `fmax` 说明天花板在哪 |
| ≈ 0 | 正好卡住 | 最理想，说明频率是"设计出来的"而不是"捡来的" |
| < 0 | 目标频率达不到 | **不能直接报目标频率**。要么降频到 `fmax` 重跑，要么先修关键路径 |

> 表 2 的"频率"一列，最稳妥的填法是：**报告实际综合所用频率 + 该频率下的 WNS**，
> 并在脚注写 `fmax ≈ xxx MHz（综合估计）`。这样无论评审怎么追问都有据可查。

## 5. 流程结构

```
make syn VARIANT=<v> TAG=<t> [CORNER=tt|ff|ss]
  │
  ├─ pdkcheck            打印库/角/约束，缺项直接报错
  └─ flow/synth/run_syn.sh
       ├─ 预检           工具、库、LEF、约束参数、孤儿 genus 进程
       ├─ 派生           周期/IO延迟/不确定度（python3 算，避免 awk 浮点差异）
       ├─ 清洗 filelist  去 // 注释与空行；**不筛 .svh**（attn_math.svh 要当设计文件）
       │                 + +define+ATTN_QB/QF/LUT（宏必须与仿真一致）
       ├─ 生成 SDC       constraints.sdc
       ├─ 调 Genus       flow/synth/syn.tcl（read_libs → read_physical → read_hdl
       │                 → elaborate → read_sdc → syn_generic/map/opt → 报告）
       ├─ 解析           flow/synth/parse_syn.py → metrics.csv（key,value）
       └─ 体检           面积必须 > 0，否则失败
```

**为什么 `syn.tcl` 整个包在 `proc` + `catch` 里**：Genus 中途报错会掉进交互模式
（提示符 `genus@root:>`），在 `runvm` 这种非交互调用里表现为"卡住不返回"，
比直接报错难查一个数量级。现在任何异常都会打 `[syn] FATAL: ...` 并 `exit 1`。

## 6. 失败模式与防线

| 失败 | 表现 | 防线 |
|---|---|---|
| 不读 LEF | 面积 0，`A₀/A` 无穷大 | 强制 `read_physical`；面积为 0 直接 fail |
| PVT 标签与库不符 | 功耗差 78% 且看不出来 | 标签由 `CORNER` 从 `pdk.mk` 派生 |
| `read_hdl -define` 与 `-f` 冲突 | `HDL-12`，直接失败 | 宏改写成 filelist 里的 `+define+` |
| 过滤掉 `.svh` | 几十条 `Unresolved subprogram reference`，仿真却是好的 | filelist 原样投喂，不做"顺手清理" |
| 孤儿 genus | 综合跑十几分钟没结果，产物目录消失 | 开跑前 `pgrep -x genus`，有就报错要求先清理 |
| 三个方案活动率不同 | mW 不可比，但表格看起来正常 | 活动率在 `pdk.mk` 里固定，写进报告 |
