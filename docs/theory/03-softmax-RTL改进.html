softmax 的 RTL 改进：从「91 拍/行」到「不再是瓶颈」

一个 16×16 的 softmax，账面上只有 256 次 exp、16 次除法、256 次归一化乘， 却吃掉 ref 实现里 69% 的乘法器面积 和每行 47% 的时间——而那 47% 的时间完全在空转。 这页把它拆开：病根在哪、三种改法各自换到了什么、以及什么时候应该停手。

四行代码换 −18% 延迟

01

先把账本摊开

softmax 按行执行，16 行彼此独立。所以整个优化问题只有两个变量： 每行要多少拍，和 一行占住多少硬件。ref 的选择是把两者都压到最小： 每拍只做一件事，一行一行的来。

相位拍数每拍做什么占用的资源
SM_MX16读 S[i][j]，与 maxv 比大小sm 读口 + 32b 比较器
SM_EX16d = maxv − S → 2^−d → 写 erow、累加 tsumsm 读口 + 减法器 + EXP2
SM_DV43等 R = 2^40 / T 长除出来仅除法器
SM_NM16p = e·R ≫ 24，饱和到 [0, 65536]erow 读口 + 17×25 乘法器
合计16 + 16 + 43 + 16 = 91 拍/行，× 16 行 = 1 456 拍

这个 91 不是估的：ref 的实测总周期 9 665 = QK 4 096 + softmax 1 456 + P·V 4 096 + 17 拍开销， 反推每行正好 91，与 recip_unit 的 41 + 2 拍长除对得上。

02

病根：43 拍里，三个资源全在晒太阳

把四个相位的资源占用画成泳道图，问题一眼就看出来了——任何时刻只有一个资源在干活。 四个资源本可以并排工作，却被一条串行的状态机排成了队列。

为什么不能直接把 43 拍砍掉

除法的 41 拍不是写坏了，是恢复余数法的固有节拍：被除数 2^40 只有 bit40 是 1， 必须逐位移进去才能得到 41 位商。想快只有三条路——并行多个除法器（面积翻倍）、 改用 Newton 迭代（要一个初始倒数表 + 2 次乘法，但舍入点变了、逐位一致就没了）、 或者让这 43 拍干别的事。第三条不要钱，前两条都要。

03

改进一：三级流水，把 43 拍的空档填掉

这是 varA 的做法，也是投入产出比最高的一步：不并行、不近似、不改任何运算， 只把一行的四个相位拆成三级，让三行同时在飞。

A
取 max + exp（32 拍）
写 erow[bank]，同时算出 tsum 交给 B 级
B
倒数（43 拍）
独占除法器。这 43 拍里 A 级正好把下一行算完（32 < 43，藏得下）
C
归一化（16 拍）
读 erow[bank] 与 rval 相乘，写 pu，顺手记非零掩码

为什么这样就逐位一致

因为行与行之间没有数据依赖——softmax 是按行定义的，第 i 行的 max、tsum、倒数只用到第 i 行自己。 流水线只是把「不同行」重叠起来，同一行内部的四步顺序一个字都没改，连舍入点都没挪。 所以这不是"数学上等价"，是逐位相同。

反过来，这套东西不能用

在线 softmax（flash attention 那套 running max / sum 重标定）：它把 max 的更新与 exp 的累加交错进行， 每步都要对已累加的部分和重新缩放。那个重标定引入了新的舍入点，结果与「先取整行 max 再 exp」不逐位相等。 判据是"与自身软件模型逐位一致"，这条路直接判死。

收益：91 → 45.5 拍/行，softmax 从 1 456 拍降到 728 拍。面积上只多了 272 个触发器（erow 双缓冲）。 这是全项目里"零数值风险"的最高性价比改动。

04

改进二：行融合，以及一个被漏算的瓶颈

varB 更进一步：既然 softmax 是按行的，那就一行走完 QK → softmax → P·V 再换下一行。 于是 sm[256]（32 bit）和 pu[256]（17 bit）整个消失， 只剩 16 深的 s_row / pu_row。省下 11 744 个触发器 + 45 914 µm² 的读 mux。

但这里有个东西值得单独说，因为它是用实测反推出来的，不是估的。

注释说 80 拍/行，实测 1 738 拍（纯计算口径）

varB 的文件头按 max(A 80, B 43, C 80) = 80 拍/行 估 1 400 拍，实测 1 738（纯计算；端到端含 768 拍装载为 2 506）。 差的 339 拍不是估错，是 erow 的 bank 占用时间没算进去—— 逐拍核算后正确的账是 82 + 8×81 + 8×126 = 1 738（前导 82、8 个奇数行 81、8 个偶数行被 bank 拖成 126）， bank 等待合计 360 拍 = 8 行 × 45—— bank_busy 是在 C 级的 P·V 走完最后一列才清的，而 C 的 P·V 段只用 pu_row 和 nzrow_r，根本不需要 erow。

改动本身只有四行——把释放挪出 P·V 分支：

// top_varB.sv  C 级归一化，c_ph == 0 的 c_j == N-1 那一拍
if (c_j == N-1) begin
  c_ph  <= 1'b1;
  c_j   <= 4'd0;
  c_acc <= 64'sd0;
  // ↓ 新增：归一化读完 erow，此刻就该还 bank
  if (c_bank == 2'd0) bank_busy[0] <= 1'b0;
  else                bank_busy[1] <= 1'b0;
end
一个反直觉的副作用（好事）

改完之后 A 级（81 拍/行）比 B 级（45 拍/行）慢，a2b_v 那个单寄存器永远不会被追上， "A 级连产两行覆盖上一行 tsum" 的隐患自动消失。 现在这个隐患不发作，纯粹是因为 2 个 bank 恰好把 A 卡住了—— 一个靠参数巧合成立的隐式反压。所以不管改不改，都建议补一条 a2b 的 SVA。

收益：1 738 → 1 423 拍（−18.1%，2026-11-14 已实测），面积代价 +0.62%（tt，映射噪声级）、零新增寄存器；对 ref 的加速比（端到端含装载口径）由 4.16× 提到 4.76×，纯计算口径下 5.56× → 6.79×。

05

改进三：除法器要不要并行？先算笔账

流水的极限是 B 级的 43 拍——除法器只有一个，它决定了 softmax 的吞吐下限。 很自然的下一个念头是：再放一个除法器，两行交错，B 级吞吐变 21.5 拍/行。

方案softmax 吞吐新增面积实际收益
1 个除法器 + 流水（varA）45.5 拍/行+272 FF基准
2 个除法器交错~22 拍/行+1 个 recip_unit
（≈ 90 FF + 46 bit 逻辑）		≈ 0
4 路并行 exp32 → 20 拍/行+3 个 EXP2（面积 ×4）≈ 0

看着矛盾，其实不矛盾：B 级不再是瓶颈之后，瓶颈就转移了。 在 varB 里 A 级是 80 拍/行（64 拍 QK + 16 拍 exp），C 级也是 80 拍/行（16 拍归一 + 64 拍 P·V）。 softmax 真正占的只有 32 拍，其余 128 拍全是 4-lane MAC 在做 Q·Kᵀ 和 P·V。 此时把除法器翻倍，等于给一条已经不被堵的路再加一条车道。

一个容易犯的错

"softmax 占了 69% 的乘法器面积，所以应该优化 softmax"——这个推理在 varB 里是错的。 它成立的前提是 softmax 同时在关键路径上。flow 融合之后它已经退到后台， 下一个瓶颈是 QK/P·V 的 4 lane。改错地方，周期数一点不动。

什么时候 2 个除法器才划算？当 A 级被压到 43 拍以下的时候——也就是 lane 数已经拉到 8 以后。 以现在 4 lane 的编排，这个改动净收益为零，不要做。

06

改进四：exp2 里切一刀，换频率不换周期

前面三条改的都是"拍数"，这条改的是"每拍能跑多快"。 ref 的关键路径 9.4 ns 主体就是 exp2_unit——五步全塞在一拍里：

为什么这条对 varA/varB 几乎零成本：它们的 A 级本来就是流水结构，exp 一拍一个元素， 加一级流水只改延迟不改吞吐，稳态周期数不变（bank 占用 +1 拍，可忽略）。 对 ref 则是实打实的 +1 拍/元素（因为它不是流水），一行 +16 拍——所以这条别在 ref 上做。

07

三条不能碰的红线

上面所有改法共用同一个前提：与自身软件模型逐位一致。这个判据把优化空间切成了两半。

不能做为什么替代
在线 softmax
running max/sum 重标定		 重标定引入新的舍入点，结果与「先取整行 max 再 exp」不逐位相等 行级流水（不改行内顺序）
改行内顺序
比如先 exp 后取 max		 d = max − S 依赖 max，顺序本身就是数值定义 —
MAC 近似
BESA 那类近位宽乘法器		 近似只允许出现在模型已经规定近似的地方（exp / 倒数 / 量化） 精确 16×16，靠 lane 数换吞吐

换句话说：能改的只有调度（谁和谁重叠、什么顺序发车），不能改的是算式。 这不是保守——判据是"逐位一致"，一旦某个乘法器开始截断，比较就变成了"大概对"，这个项目的核心论证就没了。

08

收益汇总，以及什么时候该停手

表格最后两行其实在讲同一件事：softmax 的优化在 varB 里已经做完了。 它一度是 47% 的空转，现在被压成 32 拍、藏在 80 拍的 MAC 后面。 继续抠它的除法器或 exp，周期数一点不动——下一个瓶颈是 4 lane 的 QK/P·V。

一句话总结

softmax 的 RTL 改进不是"把 exp 算得更快"，而是把等除法的 43 拍让给下一行的 max+exp。 三步走完：流水化吃掉空转（91→45.5）→ 行融合删掉缓冲（−12.5k FF）→ 把 bank 还给 A 级（−18%）。 再往下就不是 softmax 的事了。

09

三道自测

先自己想，再展开对答案。

varA 里 A 级只用 32 拍，B 级要 43 拍，为什么不是 A 级等 B 级、而是 B 级反过来追 A 级？
因为流水线的吞吐由最慢的一级决定。A 级 32 拍产出一行，B 级 43 拍消化一行， 长期看 B 级是瓶颈（吞吐 43 拍/行），A 级会不断追上去然后被 bank 卡住。 你看到的"B 追 A"是第一行刚启动时的暂态，稳态是 A 被 bank 挡住、B 满负荷。

这也是为什么 bank 占用（91 拍 ÷ 2 = 45.5）比 B 级的 43 稍微紧一点——两个瓶颈几乎打平， varA 的 softmax 就在 45 拍/行附近，而不是 43。
把 erow 从 2 bank 加到 3 bank，varA 的 softmax 会变快吗？varB 呢？
varA：几乎不变。加 bank 后吞吐上限从 45.5 降到 B 级的 43， 16 行只省 40 拍左右（1.4%），收益配不上多出来的 272 个触发器。

varB：更不该加。它的瓶颈根本不是 bank 数量，而是 bank 被多占了 64 拍。 正确做法是改释放时机（203→139），不是加 bank。加了 3 个 bank 反而会把那条 "靠 2 个 bank 限制 A 级领先"的隐式反压拆掉，a2b_v 覆盖的隐患就真会发作。
如果只允许改一行 RTL，改哪一行收益最大？
top_varB.sv 里 C 级归一化结束时的 bank_busy 释放语句。 它一行换 −18% 周期、零面积、不动任何数值语义。前提是确认 pu_row / nzrow_r 在 P·V 段确实不依赖 erow—— 确认过，pr_c 只在 c_ph==0 里被使用。

如果只能改 ref，那答案是 attn_rne_shift 的常量折叠：六个调用点里五个移位量是编译期常量， 现在每个都综合出变量桶形移位器 + 36 位减法器，白花 3% 面积还压在关键路径上。
数据来源：hw/results/metrics.csv（ref 9 665 / varA 2 855 / varB 1 738 拍，TT 25℃ GPDK045）、 docs/engineering/03-RTL方案审视.md 的面积账本、以及 rtl/core/ 三个模块逐行核对。 周期数为 start→done，不含 256 拍输出回读。
