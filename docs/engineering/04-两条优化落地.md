## 二、改了什么

### 改动 1：删掉 `om[256]`，输出改流式

三个顶层原来都是「P·V 算完 → 写 `om[i][j]` → 全部算完 → `S_OUT` 状态逐拍回读」。
但 **P·V 的完成顺序天生就是 (i,j) 字典序递增**，本来就按顺序出来，
再存 256 个 FP16 再读一遍，等于白存 4 096 个触发器 + 一套 256:1 回读多路器。

改法（三个顶层同一套）：

```verilog
// 改前
S_PV: ... if (ck == 15) begin
        om[{ci, cj}] <= y_fp;  ...
        if (ci==15 && cj==15) begin done <= 1; st <= S_OUT; end
S_OUT: begin o_vld <= 1; o_addr <= cout; o_data <= om[cout]; cout <= cout + 1; end

// 改后
S_PV: ... if (ck == 15) begin
        o_vld  <= 1'b1;
        o_addr <= {ci, cj};
        o_data <= y_fp;        // 算完当拍就出，不再落 om
        ...
        if (ci==15 && cj==15) begin done <= 1; st <= S_DONE; end
// S_OUT 整个删掉
```

配套两处细节，漏了就会错：

1. **`o_vld` 每拍必须复位。** 原来是 `S_OUT` 里无条件拉高，现在它只该亮一拍，
   所以在 `always_ff` 的 `else` 分支开头加了默认 `o_vld <= 1'b0;`。
   不加的话第一个元素之后 o_vld 会一直挂高，tb 会把后面每一拍都当成一个元素。
2. **varB 的 `done` 必须挪到 c 级。** varB 是三段流水，原来 `done` 在 `S_QK` 里
   等 `nfin == N` 才拉高，比最后一个元素晚一拍。改流式后 tb 收满 256 个就退出
   循环，`done` 晚一拍就**再也记不到**（lat 会变成 −1 并报超时）。
   现在改成在 c 级最后一行最后一拍同拍拉 `done`。

> tb 侧不用改：`tb_attn.sv:247` 的注释早就写着「done 与第一拍 o_vld 可能是同一个周期」，
> 采样是每拍都做的。三个 DUT 之前都是「先存后扫」，这条注释一直没被用上。

### 改动 2：常量移位改用「保护位 + 粘滞位」宏

`attn_rne_shift(x, sh)` 的 `sh` 是 `int` 形参 —— 对综合器来说永远是可变量。
实测（Genus 15.2）：**调用点传 localparam 不会让它折叠**，顶层关键路径上
真的躺着一坨 `csa_tree_attn_rne_shift_52_24:sub_36_9_groupi`（36 位减法器）。

数学上，算术右移 K 位的余数 `r = x - (q<<K)` **恰好就是 x 的低 K 位**
（补码对 2^K 取 floor 除法，余数就是低位）。所以 RNE 的进位条件可以从
「减法 + 两次比较」改写成经典的**保护位 + 粘滞位**：

```
进位 = x[K-1] & ( |x[K-2:0] | q[0] )
```

三个量都只是对 x 的位取用，减法器整个消失。宏定义在 `rtl/core/attn_math.svh`：

```verilog
`define ATTN_RNE_SHR(x, K) \
  ( $signed( ($signed(x) >>> (K)) + \
    ( ( ( ((x) & (64'sd1 << ((K)-1))) != 64'd0 ) && \
        ( ( ((x) & ((64'sd1 << ((K)-1)) - 64'sd1)) != 64'd0 ) || \
          ( ((x) >> (K)) & 64'sd1 ) ) ) ? 64'sd1 : 64'sd0 ) ) )
```

用到宏的 6 处（都是常量移位）：三个顶层的 `SH_Y / SH_P / SH_S`，加 `exp2_unit` 里
`d*log2e` 的 K=16 与插值修正项的 K=FB(=12)。

**仍然保留函数**的两处是真变量移位，桶形移位器逃不掉：
`exp2_unit:77` 的 2^(−n) 归一化、`fp16_quant:52` 的对齐左移。

#### ⚠ 这个宏踩过一个坑，改之前必须知道

第一版写成下面这样，**验证直接炸了：40 万组里一半不一致，全是负数**。

```verilog
// 错误写法：直接写归约
( ((x) >>> (K)) + ( (|((x) & mask)) | ... ) )   // ✗
```

原因不是数学，是 **SystemVerilog 的表达式类型传播**：`|(...)` 是 1 位**无符号**值，
一旦它和 `>>>` 出现在同一条表达式里，整条表达式被提升为**无符号**，
于是 `>>>` 退化成**长逻辑移位**。实测差值恰好是 `2^(64-K)` ——
对 x = −1、K = 16，正确结果 0，错误结果 2^48，一眼就能认出来。

修法是**不让无符号量参与运算类型传播**：把增量做成三元运算，
两端都是 64 位有符号常量（`64'sd1 : 64'sd0`），条件里的无符号量只当条件用。

第二个坑：**宏不负责 K = 0**（`1 << (K-1)` 会变成 `1 << (-1)`）。
`SH_S = 2*QF + 2 − S_FRAC` 在 QF=7 的配置下正好是 0，所以三个顶层都加了：

```verilog
localparam int K_S     = (SH_S > 0) ? SH_S : 1;
localparam bit SH_S_ON = (SH_S > 0);
...
sm[{ci, cj}] <= SH_S_ON ? `ATTN_RNE_SHR(qk_acc, K_S) : qk_acc;
```

常量条件，综合时死掉的一支不进网表，RTL 却对两种配置都成立。

## 三、怎么证明没改坏（三层验证）

### 第 1 层：宏与原函数逐位等价 —— 40 万组

新增 `tb/unit/tb_unit_rne_eq.sv`，直接引用真实的 `attn_math.svh`，
对设计里实际用到的四个常量 K = 16 / 12 / 24 / 10 做比对：

- 定向：0、±1、±2、int64 最大/最小、每个 K 的「恰好一半」±2（正负各一遍）、余数全 0 / 全 1
- 随机满 64 位 5 万组 × 4 个 K（一半是负数，专打符号扩展）
- 小范围随机 5 万组 × 4 个 K（贴着实测数据落点）

结果：**一致 400 120 组，不一致 0 组**。

这个测试已经接进单元测试链（`flow/sim/unit.sh` 的 `NAMES` 增加了 `rne_eq`）：

```bash
ONLY=rne_eq make unit VARIANT=ref TAG=unit-ref
```

## 四、面积收益的构成

以 ref 为例，总面积减少 84 662 µm²，可以拆成两块：

| 来源 | 估算 | 说明 |
|---|---|---|
| 触发器 | 4 120 × 7.524 = **31 000**（37%） | LEF 实测 SDFFQX1 面积 7.524 µm² |
| 组合逻辑 | 约 **53 700**（63%） | 256:1 回读多路器 + 地址译码 + 常量移位折叠 |

ref 的组合逻辑收益（53.7k）明显大于 varA/varB（22.4k / 19.9k），原因是：
**ref 的 `SH_S` 是真实存在的 12 位常量移位**（QF=13 时 `2*13+2−16 = 12`），
而在 10 bit 配置下 `SH_S = 0`，这一项本来就没有成本 —— 所以折叠对 ref 的
收益更大。这也顺带解释了为什么 ref 的降幅（19.2%）反而比 varA（14.1%）大。

### 关键路径搬家了

改之前，ref 的 9 449 ps 关键路径上有那坨 `sub_36_9`（RNE 的减法器）。
改之后，关键路径变成：

```
ci_reg → d_fx = maxv − sm[i][j] (sub_124_24) → exp2 的常数乘 (const_mul_53_45)
       → 加法树 → tsum_reg  （Data Path 9 451 ps，Slack 0）
```

**移位器摘掉之后，露出来的才是这个设计真正的算术路径**：softmax 的
`d = max − S` → `d·log2e` → 行和累加。这是一条纯数学链，没有白付的逻辑了。
（下一步要提 Fmax，就得在这条链上做文章：exp2 加流水级，或把行和拆成两级。）

## 五、时延口径：为什么周期数没变

tb 的 `lat` 记的是 **start → done**（`tb_attn.sv:261`），而三个 DUT 的 `done`
在改之前就落在「最后一个 P·V 元素算完」那一拍 —— 后面那 256 拍 `S_OUT`
从来就没被计进 `lat`。

所以：

- 改前：`lat = 9 665`，但真正的端到端是 `9 665 + 256`（`S_OUT` 还要扫 256 拍）
- 改后：`lat = 9 665`，端到端**就等于** `9 665`

**报告里如果要用"端到端延迟"，改前的数要加 256，改后不用加。**
本文所有表统一用 `lat`（start→done），前后可比；那 256 拍是白扔的输出时间，
不属于计算延迟。这也是为什么"删掉 om 却不改周期数"不是矛盾。
