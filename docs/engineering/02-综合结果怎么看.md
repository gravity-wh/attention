# 综合结果怎么看（Genus 15.20 · GPDK045 · 100 MHz）

> 适用：三方案（ref / varA / varB）在 CentOS VM 上跑完 `make syn` 之后。
> 一句话原则：**GUI 是给人找感觉的，报告才是给人签字的。**
> 报告里的数与 GUI 里看到的必须是同一个电路——所以 GUI 只读综合产物，不重跑综合。

---

## 1. 三个数各自的统计口径（先对齐，再看数）

| 数字 | 口径 | **不含**什么 | 谁能推翻它 |
|---|---|---|---|
| 面积 | 综合后标准单元面积（Cell）+ 线网（Net） | 布线开销、时钟树、电源网格 | 布局布线后的面积一定更大 |
| 时序 | 综合后 STA，ideal clock + 线负载模型 | 布线寄生、真实时钟树偏斜 | 只有跑完 P&R + SPEF 才作数 |
| 功耗 | 固定活动率假设（toggle 0.1 / static 0.5）下的静态估计 | 真实激励、翻转率分布 | 用仿真得到的 VCD/SAIF 反标才算实测 |

这三条写进报告时**必须原样带上**，否则"面积改善 2.12 倍"会被当成实测结论。

## 2. 这一轮的结果

来源：`runs/<tag>/syn/metrics.csv` → `make collect` → `results/metrics.csv` → `make table` → `results/tables.md`

| 方案 | TAG | 面积 (µm²) | 单元 | 寄存器 | 功耗 (mW) | WNS (ns) | 综合耗时 |
|---|---|---|---|---|---|---|---|
| ref | `ref-syn-tt` | 441 635 | 75 436 | 29 477 | 106.94 | 0.000 | 1061 s |
| varA | `varA-syn-tt` | 377 124 | 64 616 | 25 488 | 79.44 | 0.000 | 638 s |
| varB | `varB-syn-tt` | 208 232 | 35 151 | 13 513 | 44.85 | 0.000 | 376 s |

- A₀/A：ref 1.00 → varA **1.17** → varB **2.12**（面积缩小到 1/2.12）
- 三份 run 同库同角同频同活动率（`typical.lib` / TT_25C_1V20 / 100 MHz / toggle 0.1），可直接横向比。
- **周期数、时延、能耗、RMSE 四列是空的**——它们来自仿真 `runs/<TAG>/summary.csv`，而仿真那条链还没跑完。空 ≠ 0，别填。

重现命令（在 VM 上）：

```bash
cd /root/work/hw
for v in ref varA varB; do make syn VARIANT=$v TAG=$v-syn-tt CORNER=tt; done
make collect && make table      # → results/metrics.csv, results/tables.md
```

## 3. 报告导读：每份只看几行

目录：`runs/<tag>/syn/`

### `qor.rpt` —— 先看这一份

```
Timing → clk  0.0  0  0        ← Critical Path Slack / TNS / 违例路径数（ps）
Instance Count → Leaf 75436 / Sequential 29477
Area → Cell Area 348926 / Net Area 92709 / Total 441635
Max Fanout 29477 (clk)         ← 时钟扇出全部寄存器，正常
Runtime 1050.6 seconds
```

**TNS=0 且违例=0** 才叫收敛。任一非零，说明这个频率实现不了，回去改 RTL 或降频。

### `area.rpt` —— 面积花在哪

层次排行，一眼看出大头：

| 模块 | 单元 | 面积 | 占比 |
|---|---|---|---|
| `u_exp`（exp2_unit） | 2998 | 9 336 | 2.7% |
| `csa_tree_mul_114_50` | 812 | 3 062 | 0.9% |
| `mul_118_59` | 809 | 2 850 | 0.8% |
| `csa_tree_add_174_48` | 548 | 1 944 | 0.6% |

注意 `csa_tree_*` 这些名字是**综合器生成的**（进位保留加法树），不是你代码里的模块名——
它们就是乘法器/加法器被展平后的产物。看到它们说明乘法被正确推断出来了；如果看到 `*` 号被综合成
一大片逻辑而没有 `mul_*`，那才是推断失败。

### `timing.rpt` —— 关键路径

```
Path 1: MET (0 ps) Setup Check with Pin tsum_reg[20]/CK->D
  Startpoint: cj_reg[2]/CK      Endpoint: tsum_reg[20]/D
  Clock Edge 10000 | Setup -51 | Uncertainty -500 | Required 9449
```

- 路径本体：`cj_reg[2]` → 一堆 INV/BUF/AO22/AOI22 → `tsum_reg[20]`
- 10000 ps 周期，扣 51 ps setup 与 500 ps 不确定度（=5% 周期）→ 9449 ps 必须到
- **MET (0 ps)** 是"刚好压线"，不是"还有余量"。工具优化到满足就停手了。

### `power.rpt`

```
top_ref   75436   18874.431 (nW 漏电)   106916274.510 (nW 动态)   106935148.941 (nW 合计)
```

→ 106.94 mW。**单位是 nW**，直接从表里抄成 mW 会错 1e6 倍。

### `metrics.csv` —— 机器读的那一行

`key,value` 一行一个。`MISSING` 是"没取到"，不是 0。
**报告里不许出现 MISSING 的值，也不许拿 0 顶替。**

## 4. 用 GUI 看：`bash flow/synth/gui_open.sh <variant> <tag>`

### 4.1 怎么进

VM 桌面（VNC `127.0.0.1:5901`，或 VMware 窗口）里开一个**终端**，前台跑：

```bash
cd /root/work/hw
bash flow/synth/gui_open.sh ref ref-syn-tt      # 想看哪个方案换 VARIANT/TAG
```

它会做四件事：读时序库 → 读 LEF（面积来源）→ 读 `netlist.v` → 读 `netlist.sdc`，
然后把设计摊在界面上。**不跑 syn_\***，所以看到的电路与 `runs/` 里的报告是同一个。

> ⚠️ 不要 `nohup` / `&` 后台启动：Genus 读到 stdin EOF 会自己退出，
> 表现为"窗口一闪就没了"。必须在终端里前台跑。

### 4.2 界面四块（见 `docs/figures/genus-gui-总览.png`）

| 区域 | 内容 | 用来干什么 |
|---|---|---|
| 菜单栏 | File / DFT / Floorplan / Power / Timing / Tools / Windows / Help | 报告入口、窗口布局 |
| 左上 `Hierarchy` / `HDL` | 层次树，根 `top_ref`，下面是 `u_exp(exp2_unit)`、`u_f2h(fix2fp16)`、`u_quant(fp16_quant)`、`u_rcp(recip_unit)` 与一堆 `csa_tree_*` | 定位模块、看规模 |
| 右上 `Schematic` / `Layout` | 门级原理图（选中实例后出图） | 看某个模块被综合成什么样 |
| 底部状态栏 | `Design is mapped` | 确认网表已映射；若是 `unmapped` 说明读的是 RTL 不是网表 |

### 4.3 五个常用动作

1. **看层次与规模**：Hierarchy 里展开 `top_ref`。括号里是综合后的单元名（如 `exp2_unit`），
   不是 RTL 模块名时说明该层被展平了。
2. **看原理图**：在 Hierarchy 里选中（双击）一个实例 → 右上 Schematic 出图。
   命令行等价：`gui_sv_cone [get_db insts u_exp]`（若 `get_db` 找不到，先 `get_db -hier insts *u_exp*` 确认路径）。
3. **看关键路径**：菜单 `Timing` 或直接敲
   `report_timing -max_paths 20 -nworst 20`，
   再把路径上的实例名拿到 Hierarchy 里搜，逐个摊开看是不是被综合成了奇怪的结构。
4. **重看面积/功耗**：`report_area` / `report_power`，随时可敲，不改电路。
5. **窗口太小**：默认 600×420。手动拉大或双击标题栏最大化；`wm geometry . 1800x980+10+10`
   在这个版本的 WM 下不一定生效，别指望。

### 4.4 GUI 里**不要**做的事

- ❌ 在 GUI 里改约束、重跑 `syn_opt`，然后把新数字抄进报告——那是**另一次综合**，口径变了。
- ❌ 用 GUI 里 `report_area` 的数去覆盖 `metrics.csv`——两者同源，但后者带 commit/tag 可追溯。
- ❌ 只看原理图"感觉挺合理"就下结论——图是给人找感觉的，结论要靠报告里的数。

## 5. 数字陷阱清单（这次踩过或差点踩的）

| 现象 | 真因 | 处理 |
|---|---|---|
| 面积报 **0** | 没 `read_physical -lef`（演示库 .lib 里 area 全是 0.0） | 流程已强制读 LEF，并在面积为 0 时报错退出 |
| 功耗 **138 mW**（虚高） | `set_switching_activity` 在 15.2 里不存在，活动率没设成 | 已改用端口属性 `lp_asserted_toggle_rate/probability`，现为 106.9 mW |
| `metrics.csv` 大面积 **MISSING** | `get_attribute` / `get_timing_paths` 在 15.2 里不存在 | 改为由 `parse_syn.py` 解析报告文本（带显式单位） |
| **WNS 恰好 0.000** | 工具"满足即停"，不代表 100 MHz 是上限 | 真实 f_max 要扫频才有；`fmax_mhz=100` 只是估算下限 |
| `RPT-13` 时钟周期不符告警 | 端口上的 asserted 活动率（0.1/拍）与 SDC 的 10 ns 周期被工具对账 | 三方案**同一条告警**，相对比较有效；要绝对数就把 `clk` 端口排除在活动率设置外再跑一次 |
| `commit` 列 `NOT-A-REPO` | VM 上的 `/root/work/hw` 不是 git 仓库 | 要么在 VM 里 `git init` 并提交，要么改成"从本地仓库 rsync 过来的 <sha>" |

## 6. 下一步（还缺什么）

1. **仿真链没跑完**：`runs/varA/` 只有 `simv.daidir`，没有 `summary.csv`/`INFO.txt`，
   所以表 2 的周期数/时延/能耗/RMSE 四列是空的。→ `make sim VARIANT=<v>` 补上。
2. **TAG 没对齐**：仿真用的是 `runs/varA`，综合用的是 `runs/varA-syn-tt`，
   `collect.py` 因此把它们算成两行、`SYN-ONLY`。合并只需挪目录，不用重跑：
   `mv runs/varA-syn-tt/syn runs/varA/syn`（ref/varB 同理）。
3. **三个角**：`make synall VARIANT=<v> TAG=<t>` 跑 tt/ss/ff，签核才需要。
