## 1. 三层分工与文件流

| 层 | 在哪 | 放什么 | 铁律 |
|---|---|---|---|
| 真源 | Windows / NAS 上的工程根 | 源码、脚本、配置、`results/` | git 只在这里提交 |
| 中转 | 共享目录（hgfs / SMB） | 同步副本 | **绝不在共享盘上编译或仿真** |
| 执行 | VM 本地盘 `/root/work/hw` | `runs/`、波形、综合与 P&R 产物 | 所有工具只在这里跑 |

```bat
:: Windows：NAS → 共享目录（增量，排除 runs/.git/波形/可执行）
E:\candence_env\share\sync_from_nas.bat
```

```bash
# VM：共享目录 → 本地盘，然后才编译
/root/work/prepare.sh && cd /root/work/hw
```

两条必须记住的操作事实：

1. **hgfs 上跑仿真会慢一个数量级**（FUSE 写 `simv` 中间文件与覆盖率库）。`prepare.sh` 就是 `cp -a` 到本地盘。
2. **调用 `vmrun.exe` 必须设 `MSYS_NO_PATHCONV=1`**，否则 Git Bash 把客户机路径 `/bin/echo` 转成 Windows 路径，
   报「文件未找到」，错误信息完全指不到真因。

## 2. 仿真工具栈

### 2.1 为什么只有一个仿真器

| 能力 | iverilog 12 | VCS 2023.12 |
|---|---|---|
| SVA 断言 | ❌ | ✅ |
| 功能覆盖率（covergroup + urg） | ❌ | ✅（报告受 license 限制，见 §11.1） |
| UVM | ❌ | ✅（`$VCS_HOME/etc/uvm`） |
| 波形给 Verdi | ⚠ 只有 VCD | ✅ FSDB / KDB |
| 编译本工程 RTL | 秒级 | **1～2 s** |

验证占 30 分，其中「验证充分性」要靠覆盖率与断言说话；而 VCS 编译这个规模只要 1～2 秒，
比「本地装 iverilog 再同步」还快。所以 iverilog 已退役，**单一仿真器：VCS**。
verilator 只在 `make lint` 里做静态检查（`--lint-only -Wall`），不承担签核。

### 2.2 编译命令逐项解释（`flow/sim/build.sh`）

| 选项 | 作用 | 去掉会怎样 |
|---|---|---|
| `-full64` | 64 位编译 | license/内存受限，跑不了 69k 单元级设计 |
| `-sverilog` | SystemVerilog 语法 | `attn_pkg` / `enum` / `covergroup` 全报错 |
| `-timescale=1ns/1ps` | 时间单位 | tb 的 `#` 延时失真，周期数算错 |
| `-debug_access+all -kdb` | Verdi 的 KDB 数据库 + 全信号可见 | 只能看 VCD，无法用 Verdi 追信号 |
| `-line` | 行覆盖率信息 | 覆盖率只有条件/翻转 |
| `-cm ...`（`CM=1` 才加） | 行/条件/FSM/翻转/分支采集 | 默认不加：URG 出不了报告，只拖慢仿真（§11.1） |
| `-pvalue+tb_attn.CLK_MHZ=$CLOCK` | 把频率传进 tb | 周期数换算与综合频率脱钩 |
| `+define+DUT=top_xxx` | **编译期选被测顶层** | 三个方案要三份 tb，对比条件不再天然一致 |
| `+define+ATTN_QB/QF/LUT` | 数值格式宏 | RTL 退回 `attn_pkg` 默认值，与向量对不上 |
| `-f rtl/<v>/filelist.f` | 方案隔离 | 三个方案的模块混编，重名冲突 |
| `-Mdir runs/<TAG>/csrc` | 中间文件落 TAG 目录 | 多 TAG 并行时互相覆盖 |
| `-l runs/<TAG>/build.log` | 编译日志 | 复现链断掉（报告数字追不回来） |

运行侧（`run.sh`）：`+VECDIR`（`tb/vectors/s<seed>[_full]`）、`+CFG`（决定读哪份 `_exp_<cfg>.hex`）、
`+CAT`、`+N`、`+VERBOSE`，外层 `timeout 300` 兜底（正常一类 2～5 s，60 倍余量），
`SIMV_NAME` 可改名（避免另一条跑道的 `pkill -f simv` 误杀）。

### 2.3 黄金模型与向量

- 编译器：**gcc，C11**，`-O2 -ffp-contract=off -fno-fast-math`。
  `-ffp-contract=off` 不是性能选项：gcc 默认会把 `a*b+c` 收缩成 FMA，改变 double 末位，
  `ref.hex` 就会出现无意义的 diff。
- 复现的两条硬要求：`dumpvec` 用 `"wb"` 写文件（否则 Windows CRT 把 `\n` 翻成 CRLF）；
  `attn_ref` 不调 libm 的 `exp()`（否则跨 gcc 版本差 1～2 ULP）。
- 实测：Linux gcc 4.8.5 与 Windows gcc 15.2 生成的 37 个受跟踪文件**逐字节相同**。

## 4. 后端工具

| 项 | 值 |
|---|---|
| 工具 | Innovus **15.20**，`/opt/cadence/INNOVUS152` |
| 输入 | Genus 的 `netlist.v` + `netlist.sdc` + 单元 LEF + **生成的 tech LEF** + 3 角 MMMC |
| 多角视图 | `flow/pnr/mmmc.tcl`：`ls_tt/ss/ff` × `rc_tt/ss/ff`；setup 用 ss，hold 用 ff，tt 只看面积功耗 |
| 寄生提取 | `create_rc_corner -qx_tech_file <qrcTechFile_RCgen>` + `extractRC`（medium effort） |
| 布线层 | 信号层 **M2–M5**（`setNanoRouteMode -routeBottomRoutingLayer 2`）；M1 只留单元内部电源轨 |
| 线程 | `PNR_CPUS` 按内存算：≥14 GB → 6，10–13 → 4，8–9 → 3，<8 → 2 |
| 内存护栏 | RSS ≥ 12 GB 告警、≥ 14 GB 主动终止（`MEM_WARN_GB` / `MEM_KILL_GB`） |
| 断点续跑 | CTS 后存 `after_cts.enc`，`make pnr-resume` 从 CTS 续跑 |
| 实测 | CTS ≈ 40 min / 3.4 GB；detail route 4 线程 ≈ 56 min / 13.2 GB；提取 + STA ≈ 2 min |

**为什么 tech LEF 要自己生成**：SMIC40 交付包里唯一的 `.lef` 是 macro-only（0 个 LAYER），
没有官方 tech LEF。`gen_techlef.sh` 走 `techfile.tf → Virtuoso OA tech.db → lefout -techOnly`，
再做三步后处理：剥 LEF58 扩展属性（否则 `IMPLF-111`）、间距表单调化（否则 `NRFL-374`）、
按 VIARULE 补显式 VIA（否则 `NRDB-158`）。**这是 DRC 38 万 marker 的根源之一，报告必须注明非官方。**

## 7. 角、PVT 与约束（这些是实验条件，不是调参）

### 7.1 三个角

| 角 | 库文件后缀 | PVT 标签 | 温度 | 用途 |
|---|---|---|---|---|
| tt | `tt_typical_max_1p10v_25c` | `TT_25C_1V10` | 25 °C | 典型 / 面积功耗 |
| ss | `ss_typical_max_0p99v_125c` | `SS_125C_0V99` | 125 °C | 签核 setup |
| ff | `ff_typical_min_1p21v_m40c` | `FF_M40C_1V21` | −40 °C | 签核 hold |

PVT 标签由 `CORNER` 从 `config/pdk.mk` 派生，**标签与实际加载的 `.lib` 必然一致**。
⚠ 题面模板里的 `tt_25C_0.90V` 是占位符；按 0.9 V 报而库是 1.10 V，功耗会差约 49%。

### 7.2 综合约束（`config/pdk.mk`，三方案逐字相同）

| 约束 | 取值 | 理由 |
|---|---|---|
| 时钟 | 100 MHz（10 ns），三方案同频 | 曾给 varA/varB 配 200 MHz，等于白送时延优势，已纠正 |
| 时钟不确定性 | 5% 周期 | 综合阶段没有时钟树 |
| 输入驱动 | `BUFH_X4M_A9TR40`（不用 ideal） | ideal 给 0 转换时间，抹平方案差异 |
| 输入转换 | 0.05 ns | 与驱动单元量级匹配 |
| 输出负载 | 0.016 pF | ≈ 扇出 2 的门 + 一小段线 |
| I/O 延迟 | 各 25% 周期 | 反映外面还有一级寄存器 |
| `rst_n` | `set_false_path` | 异步复位 |
| 活动率 | toggle 0.1 / static 0.5 | 功耗必须建立在明确假设上 |
| 时钟门控 | 显式禁止，事后数 `*ICG*` | 一个插一个不插，面积差就混进无关变量 |

全套值用 `make pdkcheck` 打印并核对文件存在性。

## 8. 环境变量与 license

```
VCS_HOME    = /root/synopsys_apps/vcs/vcs/V-2023.12-SP2
VERDI_HOME  = /root/synopsys_apps/verdi/verdi/V-2023.12-SP2
SCL_HOME    = /root/synopsys_apps/scl/2021.03

```

- 环境变量写在 `/etc/profile.d/synopsys.sh`，并在 `/etc/bashrc` 兜底 `source`。
  **必须两处都有**：早期只写在 root 的 `.bashrc`，登录 shell 有、`make` 子进程没有，表现为「工具找不到 license」。
- `LM_LICENSE_FILE` 里混进了 Cadence / Mentor 的路径（`/opt/cadence/IC617/...`、`/opt/mentor/license/license.dat`）。
  实测摘掉不变快，暂不动；但它是「工具突然找授权变慢」的第一嫌疑点。

## 9. 怎么复核：四条自检命令

| 命令 | 回答的问题 | 期望 |
|---|---|---|
| `make env` | 这台机器的工具版本、PDK 文件、license 到底是什么 | 生成 `runs/env/ENV.md`；缺失项会被点名 |
| `make pdkcheck` | 库 / 角 / qrc / 门级模型 / techfile 是否齐、约束是否自洽 | 全部 `✓`；只告警不中断（Windows 侧本来没有库） |
| `make flowtest` | 仿真链路（tb / 驱动 / 判据 / 退出码）本身是否好的 | 不需要 RTL，约 18 s（热态） |
| `make preflight` | 仓库是否自相矛盾（数值格式三处同源、派生物没进库、TAG 配对…） | 全绿才提交 |

手工复核版本：

```bash
vcs -ID | head -2

genus -version | head -2
innovus -version | head -2
md5sum /opt/cadence/PDK/smic40/smic40ll/techfile.tf
```

## 10. 性能基线（换机器时用来判断「是不是变慢了」）

| 动作 | 热态 | 冷启动（开机后第一次） |
|---|---|---|
| `vcs` 编译最小 DUT | **8.9 s** | 40～138 s |
| `simv` 跑完（0 周期） | 4.6～5.6 s | 23～26 s |
| `make flowtest`（编译 + 两次仿真） | **17.5 s** | 80 s |

| 后端 | 线程 | 峰值 RSS | 耗时 |
|---|---|---|---|
| Genus 综合（69k 单元） | 4 | 1.5 GB | 15～18 min/角 |
| Innovus CTS | — | 3.4 GB | ~40 min |
| Innovus detail route | 4 | 13.2 GB | ~56 min |
| 提取 + 后布线 STA | — | 1.9 GB | ~2 min |

冷启动的 40 秒不是 CPU / DNS / license 问题：strace 看到的是几千个 31 ms 的 `poll()` 空等，
全在进程内部。**开机先跑一次 `make flowtest` 预热**，之后都是秒级。
内存与并发的完整策略见 `06-内存与并发策略.md`。

## 11. 已知限制：报告里必须带的限定语

| # | 限制 | 后果 | 报告怎么写 |
|---|---|---|---|
| 1 | **URG license 不含该特性**，`urg -dir simv.vdb` 崩在 `covdb_get_license()` | 出不了行覆盖率百分比 | 证据链用「六类回归表 + `runs/<TAG>/sim_<cat>.log`」；`-cm` 默认关 |
| 2 | **tech LEF 非官方**（从 `techfile.tf` 生成 + 后处理） | DRC 384,913 marker 不可签核 | 必须带两条：① tech LEF 为工具生成；② 未做 `optDesign -postRoute` |
| 3 | **无 PrimeTime / PowerArtist** | 面积/时序/功耗只能出自同一次综合 | 写「综合估计，非签核」；三者同网表，相对值有效 |
| 4 | **Genus 15.20 无 `set_switching_activity`** | 功耗用工具默认活动率 | 写「工具默认活动率下估计」；`pdk.mk` 里的申报值未生效 |
| 5 | **GPDK045 的 `.lib` 面积为 0** | 必须靠 LEF 补；混用会得到 0 面积或综合失败 | 只作早期对照；正式数字一律 SC9MC |
| 6 | 面积/功耗口径 | 面积是纯 cell 面积（不含布线/时钟树/IO/SRAM）；功耗是静态估计 | 每个数字后接边界说明（`06`/`05` §5） |
| 7 | 40 nm 与 L294 里的 55/90 nm 不可直接比 | 只能比趋势 | 引用倍率时标「跨工艺，仅趋势」 |

| `git pull` 502 / 连不上 GitHub | 环境变量代理 `127.0.0.1:62185` 是坏的 | 显式用 Clash 混合端口：`git -c http.proxy=http://127.0.0.1:7897 pull` |

| `genus` 无声退出、无报告 | 8 线程在小内存机上被 OOM kill | `SYN_CPUS=4`；看 `dmesg`；重跑 |
