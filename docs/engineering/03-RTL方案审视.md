# RTL 方案审视（前端设计审查）

> 审查对象：`rtl/` 全部 10 个文件（1,533 行）+ 综合产物 `runs/*-syn-tt/`
> 审查时间：2026-10-30
> 结论层级：能综合、能收敛、数值契约自洽；**但效率对比的归因链有断裂，且三方案都还有 15~22% 的面积是"写法"造成的、不是电路需要的。**

---

## 零、先说结论

三句话：

1. **这是一个"存储受限"的设计，不是"算力受限"的。** 三个方案的单元面积里 62~64% 是触发器阵列；功耗差异 2.39× 也基本等于触发器数量比 2.18×。想省面积，第一优先级是省寄存器，不是抠乘法器。
2. **`ref → varA` 的 1.17× 面积收益，几乎全部来自位宽 16→10，与 4-lane 并行无关。** 并行化本身反而增加了组合逻辑。这条对比混了两个变量，现在**不能**在报告里说"并行带来 17% 面积收益"。
3. **`varA → varB` 的 1.81× 是干净的单一变量**（4 lane 相同，只差"全矩阵展开 vs 行融合"），这条可以放心用。

另外一句提醒：三个方案的 WNS 都是 0，但周期 10 ns 里已经用掉 9.2~9.4 ns。**slack=0 是"用尽"，不是"宽松"**——面积是"100 MHz 约束下的面积"，改频率必须重跑。

## 一、三方案到底变了哪些变量

| 方案 | Q/K/V 位宽 | lane | 存储策略 | softmax 调度 | 稀疏跳过 |
|---|---|---|---|---|---|
| `ref` | **16/13** | 1 | 全矩阵展开：`sm[256]` + `pu[256]` | 逐行串行 | 无（注释里有、代码里没有，见 P2-1） |
| `varA` | **10/7** | 4 | 全矩阵展开：`sm[256]` + `pu[256]` | 三级流水（A max+exp / B 倒数 / C 归一） | 有，按 4 个一组 |
| `varB` | 10/7 | 4 | **行融合**：`s_row[16]` + `pu_row[16]` | 三级流水，P·V 并入 C 级 | 有 |

把这张表读成"变量隔离矩阵"就看出问题了：

- `ref → varA`：**同时改了位宽、并行度、存储调度三件事**。所以 1.17× 无法归因。
- `varA → varB`：**只改了存储策略**。1.81× 可以归因，且归因结果很干净（见 §4）。

### 为什么这不是吹毛求疵

报告要论证的是"某一种结构优化带来了多少收益"。如果 A 和 B 之间差了三个变量，
那这个数字在答辩时被问一句"你怎么知道不是位宽带来的"就站不住了。
而按下面的拆解，那位老师问得正好在点子上——**收益确实主要是位宽带来的**。

## 二、面积解剖：62% 是触发器

### 2.1 器件面积（GPDK045 LEF 实测）

```
SDFFQX1  = 4.4 × 1.71 = 7.524 µm²   ← 实际主力；scan-mux 被拿来当 load-enable 用（§5 P1-3）
MDFFHQX1 = 5.0 × 1.71 = 8.550 µm²   ← 原生带使能 DFF（D0/D1/S0）
DFFQXL   = 3.2 × 1.71 = 5.472 µm²   ← 库里最小，但没有使能引脚
DFFQX1   = 3.4 × 1.71 = 5.814 µm²
DFFQX2   = 3.8 × 1.71 = 6.498 µm²
NAND2X1  = 1.043 µm²
AOI22X1  = 2.394 µm²
```

> 注意：`typical.lib` 里**所有单元的 area 都是 0.0**。Genus 报的 Cell Area 完全来自
> `read_physical -lef`。这就是 `pdk.mk` 里那条注释警告的"忘了读 LEF 会算出面积改善 ∞ 倍"。

### 2.2 触发器账本

| 方案 | 单元面积 | SDFF | MDFF | 触发器面积 | **占比** |
|---|---|---|---|---|---|
| ref | 348,926 | 28,489 | 695 | 220,293 | **63.1%** |
| varA | 297,148 | 22,672 | 2,304 | 190,283 | **64.0%** |
| varB | 163,080 | 13,068 | ~445 | 102,129 | **62.6%** |

而 `ref` 的 29,477 个寄存器可以逐项对上：

```
qm/km/vm  3 × 256 × 16 = 12,288
sm        256 × 32     =  8,192
pu        256 × 17     =  4,352
om        256 × 16     =  4,096
erow       16 × 17     =    272
                        ───────
                         29,200  （+ 状态机/计数器 ≈ 277 → 29,477）✓
```

**账本能对上，说明面积构成已经完全清楚了：逻辑只占三分之一。**

### 2.3 功耗也是同一件事

| 方案 | 总功耗 | 触发器数 | 功耗比 | 触发器比 |
|---|---|---|---|---|
| ref | 106.94 mW | 29,477 | 1.00 | 1.00 |
| varA | 79.44 mW | 25,488 | 0.743 | 0.865 |
| varB | 44.85 mW | 13,513 | 0.419 | 0.458 |

功耗比和触发器比同向且接近。**漏电只有 8.5~18.9 µW，全部功耗都是动态的**；
动态功耗主体是寄存器阵列的时钟与翻转，而不是那几个乘法器
（`u_exp` 4.87 mW、`mul_118_59` 1.46 mW、`u_quant` 5.36 mW，加起来才 11%）。

## 三、`ref → varA` 的 64,511 µm² 到底来自哪

逐项拆：

| 项 | 寄存器变化 | 面积影响 | 来源 |
|---|---|---|---|
| Q/K/V 位宽 16→10 | −4,608 FF | **−34,672** | 位宽 |
| erow 双缓冲（流水需要） | +272 FF | +2,047 | 并行化 |
| nzrow 掩码 | +256 FF | +1,926 | 稀疏跳过 |
| 组合逻辑净变化 | — | **−21,768** | 也是位宽（乘法器 16×16→10×10、mux 变窄） |
| 其余（状态机等） | — | −2,044 | — |
| **合计** | −4,080 FF | **−64,511** ✓ | |

**读法：寄存器这一块，省下的 4,608 个全部来自位宽；并行化反而净增了 528 个（双缓冲 + 掩码）。**

组合逻辑也减少了 21,768 µm²，同样是因为位宽：`ref` 的是 16×16 乘法器和 16 位宽的 256:1 mux，
`varA` 是 10×10 和 10 位宽。**4-lane 并行把 1 个乘法器变成 4 个，但每个小了很多。**

所以：

> **`varA` 相对 `ref` 的价值在时间（9,872 → 3,264 拍，3.0×），不在面积。
> 面积那 1.17× 是位宽送的，不是并行送的。**

这不是说 varA 做得不对，而是报告里必须把这两件事分开写。混着写会被一针见血地问倒。

### 怎么补上这个缺口（两条路，选一条）

| 做法 | 工作量 | 得到什么 |
|---|---|---|
| 补跑 `ref` 用 QB=10/QF=7 的综合 | 一条命令 + 18 min | 干净的"并行度"单变量对比 |
| 补跑 `varA` 用 QB=16/QF=13 的综合 | 同上 | 同上，反方向 |

改了 `config/variants.mk` 里 ref 的 `qb_ref/qf_ref` 再 `make syn VARIANT=ref TAG=ref-10b-tt`
即可，RTL 一行不改（`attn_pkg` 的宏本来就是编译期注入的）。

## 四、`varA → varB` 的 168,892 µm² 是干净的

| 项 | 寄存器变化 | 面积影响 |
|---|---|---|
| 去掉 `sm[256]`（32 bit） | −8,192 FF | −61,637 |
| 去掉 `pu[256]`（17 bit） | −4,352 FF | −32,742 |
| 新增 `s_row[16]`（32 bit） | +512 FF | +3,852 |
| 新增 `pu_row[16]`（17 bit） | +272 FF | +2,047 |
| 新增 `nzrow_r[16]` | +16 FF | +120 |
| 组合逻辑（mux 256:1 → 16:1） | — | −45,914 |
| 其余 | — | −24,588 |
| **合计** | −11,744 FF | **−168,892** ✓ |

**行融合的收益分两半：一半是触发器（−88,154），一半是读写 mux（−45,914）。**

这一点值得在报告里单独强调，因为它是个不显然的结论：
省掉一个 256 深的寄存器堆，省的不只是 256 个触发器的面积，还有访问它所需的 256:1 mux。
后者在 `varA` 里是 32 位宽 × 256 选 1，约 8,192 个 mux2，面积和触发器本身相当。

## 五、RTL 层面的问题清单

按"影响多大"排序，每条给出证据和改法。

### P0-1　延迟、精度、能量三列全空，报告的核心指标缺失

`results/metrics.csv` 现在的实际内容：

```
cycles  delay_us  fmax_mhz  energy_nj  rmse  maxae  mism  →  全空
```

而且 `runs/varA/` 里只有 `build.log` + `csrc` + `simv.daidir`，
**三个方案从来没有跑过系统级仿真**。

后果：
- 没有 `cycles` 就没有 `E = P × T`，能量效率这一列算不出来；
- 没有 `RMSE` 就**无法证明 10 bit 位宽是安全的**——而这恰恰是 `varA/varB` 省面积的主要手段；
- 报告如果写"能效提升 14×"，那只是面积×功耗的推断，不是测出来的。

**这是当前最大的缺口，优先级高于任何 RTL 优化。**

### P0-2　`lat` 的口径会让周期数少算 256 拍

`tb/sys/tb_attn.sv:261`：

```systemverilog
if (lat < 0 && done === 1'b1) lat = n;
```

`lat` 记的是 **start → done**。而三个 DUT 的 `done` 都在 P·V 结束时拉高，
之后还有 `S_OUT` 的 256 拍输出。所以 tb 报的延迟**不含输出时间**。

三个方案都少 256 拍，相对比较不受影响，但：
- 报告里写"9,872 拍"必须注明"到 done 为止"；
- 若拿它和面积算 AT 积，绝对值差 2.6%。

**改法**：在 `while` 循环结束后取 `n` 作为总周期数，另存一列 `cycles_total`。

### P1-1　`om[256]` 是 4,096 个触发器白存（占 varB 面积的 19%）

三个方案都是"先算完存进 `om[256]`，再从 `S_OUT` 逐拍扫出来"。

但 P·V 的输出顺序天然就是行主序 `0..255` 递增，**根本不需要缓存**。
而 tb 早就明确支持流式输出——`tb_attn.sv:247` 的注释写着：

> 关键点：done 与第一拍 o_vld 可能是同一个周期（流式输出的实现都是这样）。

也就是说 **tb 作者预期了流式实现，三个 DUT 却都绕了远路**。

代价：

| 项 | 面积 | 占该方案 |
|---|---|---|
| 4,096 个 SDFF | 30,818 | ref 7.0% / varA 8.2% / varB **14.8%** |
| 256:1 × 16 bit 读 mux | ≈ 9,800 | ref 2.2% / varA 2.6% / varB 4.7% |
| **合计** | **≈ 40,600** | ref 9.2% / varA 10.8% / **varB 19.5%** |

**改法**：P·V 最后一拍直接 `o_vld <= 1; o_addr <= {ci,cj}; o_data <= y_fp;`，
删掉 `om` 和整个 `S_OUT` 状态。输出地址仍是严格递增，协议不变。

这是**三方案共同**的最大单项浪费，改一处三套同时受益，且不改变任何数值结果。

### P1-2　`attn_rne_shift` 的 `sh` 是变量，导致常量移位也综合成了变量移位器

`attn_math.svh:28`：

```systemverilog
function automatic logic signed [63:0] attn_rne_shift(input logic signed [63:0] x, input int sh);
```

`sh` 声明为 `int` 变量，于是**每个调用点**都会综合出：
64 位变量桶形移位器 + 64 位变量左移 + 36 位减法器 + 38 位比较器 + 相等比较器。

但实际 6 个调用点里，**5 个的移位量是编译期常量**：

| 调用点 | 移位量 | 是否常量 |
|---|---|---|
| `fp16_quant.sv:52` | `-sh` | 变量（必须通用） |
| `exp2_unit.sv:52` | `16` | **常量** |
| `exp2_unit.sv:66` | `FB`(=12) | **常量** |
| `exp2_unit.sv:73` | `n` | 变量（必须通用） |
| `top_*.sv` ×3 | `SH_S` / `SH_P` / `SH_Y` | **常量** |

证据就在面积报告和关键路径里：

```
csa_tree_attn_rne_shift_52_24:sub_36_9_groupi   304 cell  1,298 µm²
csa_tree_attn_rne_shift_73_14:sub_36_9_groupi   175 cell    700 µm²
attn_rne_shift_73_14:gt_38_9                    116 cell    381 µm²
attn_rne_shift_73_14:sll_37_13                  105 cell    219 µm²   ← 变量左移
csa_tree_attn_rne_shift_121_17:sub_36_9         127 cell    539 µm²
final_adder_attn_rne_shift_121_17:sub_36_9      389 cell  1,255 µm²
...
```

`r = x - (q <<< sh)` 这一行，在 `sh` 为常量时**根本不需要减法器**：
`q <<< 16` 就是位截取，`r` 就是 `x[15:0]`。现在它被综合成一个真实的 36 位减法器。

_total 粗算：三个方案各有 13,000~14,000 µm² 花在舍入上，占总面积 3.1%、组合逻辑的 11%。_

**更糟的是它在关键路径上。** `ref` 的 9,449 ps 路径（见 §6）直接从
`sub_117_22`（`d_fx` 减法）穿过 `u_exp/csa_tree_mul_52_71`（乘法），
再穿过 `csa_tree_attn_rne_shift_52_24:sub_36_9_groupi`——**那条减法器就压在关键路径上**。

**改法**：加一个常量版本，让 `sh` 做参数：

```systemverilog
// 宏比 function 更适合：sh 必须是编译期常量才能折叠
`define ATTN_RNE_SHIFT_C(x, SH) \
  ((SH) == 0 ? (x) : rne_const(x, (SH)))
```

或者直接为三个常量点手写展开（`SH_S/SH_P/SH_Y` 各一个 `function automatic ... #(parameter int SH)`）。
**面积省约 3%，关键路径缩短 1~1.5 ns（Fmax 提升 10~15%）。**

### P1-3　扫描 DFF 不是浪费——这是 Genus 在吸收 load-enable（一条被我自己推翻的猜想）

**先说结论：这里没有免费面积可拿，不要动。**

我一开始的判断是：`ref` 的 28,489 个触发器全是 `SDFFQX1`（7.524 µm²），
而库里最小的是 `DFFQXL`（5.472 µm²），小 27%，三个方案各能省 11~12%。

**判断错了。** 证据在网表里：

```
SDFFQX1 \erow_reg[0][1] (.CK(clk), .D(n_48803), .SE(n_766),
                         .SI(\erow[0][1]), .Q(\erow[0][1]));
                            ↑ SI 接回自己的 Q    ↑ SE 接一个使能信号
```

`SDFFQX1` 的 lib 定义是 `next_state : "((SE SI) + (!SE D))"`。当 `SI` 自环时：

| SE | 实际行为 |
|---|---|
| 0 | 载入 `D`（新值） |
| 1 | 载入 `SI` = 自己的 `Q`（**保持**） |

也就是说 **Genus 把 scan-mux 当成 load-enable mux 用了**。而这不是偶然——
`erow` 只在 SM_EX 阶段写、`qm/km/vm` 只在 `ld_en` 时写、`sm/pu/om` 同理，
**这些存储阵列全都需要"使能 + 保持"，SDFFQX1 一个单元就解决了。**

算笔账（换 `DFFQXL` + 外部 2:1 mux）：

```
SDFFQX1 单独                     = 7.524 µm²
DFFQXL + AOI22X1（每 10 位一组）  = 5.472 + 2.394 = 7.866 µm²   ← 反而更贵
```

**所以这是工具的正确优化。** 旁证：我拿 100 个纯触发器（每拍无条件更新、不需要使能）
做了个微型实验，Genus 那边老老实实选了 `DFFQXL`（547 µm² / 100 个）——
可见它并不是"偏爱扫描单元"，而是按是否需要使能来选。

唯一残留的小代价：`varB` 的关键路径终点是 `om_reg[9][11]/SI`，要穿过这个 mux。
但删掉 `om`（P1-1）之后这条路径整个消失，所以不值得为它单独做什么。

> 写这一段是因为它值得记住：**综合器的"怪选择"先看端口接什么，再下结论。**
> 我差点把一条"能省 11%"的错误建议写进修改清单。

### P1-4　`sm` 用 32 位存了实际只需要 24 位的值

`top_ref.sv:63` / `top_varA.sv:63`：

```systemverilog
logic signed [31:0] sm [0:NELEM-1];   // S，F=S_FRAC
```

但 S 的幅值上界是算得出来的：`|Q|,|K| ≤ 4`，16 项点积 `/4` → `|S| ≤ 64`，
`F=16` → `|S_fx| ≤ 2^22`，**24 位 signed 足够**。

用 32 位浪费 8 × 256 = **2,048 个触发器 = 15,409 µm²**（ref 3.5% / varA 4.1%）。

题面限定 `|Q|,|K| ≤ 2` 的话，上界更小（`|S_fx| ≤ 2^20`，21 位），但为防极端用例留 3 位余量取 24 位是稳妥的。

**注意**：这条只对 `ref/varA` 有效，`varB` 已经用行融合把 `sm` 整个删掉了。

### P2-1　`ref` 注释承诺的 `vld_k` 稀疏门控**根本没有实现**

`top_ref.sv:19-22` 写着：

```
//  3) 稀疏跳过（BASU / P×V 的 0-PP 省略）：softmax 后大量 p 会被量化成 0，
//     P·V 时这些乘法对结果没有任何贡献。本实现里用 vld_k 标出非零 p，
//     乘法器输入被门控成 0（省翻转，不改结果）。
```

但全仓库搜 `vld_k` 只有这一行注释：

```
$ grep -rn "vld_k" rtl/
rtl/ref/top_ref.sv:20:  // ...本实现里用 vld_k 标出非零 p，
```

`top_ref.sv` 里 `pv_prod` 没有任何门控，就是裸乘。**注释描述了一个不存在的实现。**

危害：报告里若写"ref 用 0-PP 门控节省翻转"，那是假的；如果评委顺着注释去代码里找
`vld_k`，会直接找到"注释与代码不符"这个更糟的问题。

**改法**（二选一）：
- 老实删掉这段注释，改成"ref 不做稀疏处理，把门控留给 varA/varB"；
- 或者真加上 `assign pv_prod = pu[{ci,ck}]==0 ? 0 : ...`（但会增加 256 个 mux，且 `ref` 的面积基准会变）。

推荐前者——`ref` 的定位本来就是"什么都不优化的分母"。

### P2-2　`ref` 的 `filelist.f` 少了 `attn_math.svh`

`rtl/varA/filelist.f` 和 `rtl/varB/filelist.f` 都把 `rtl/core/attn_math.svh` 单独列成设计文件，
并且都写了同一段警告：

> ⚠ attn_math.svh 必须以**设计文件**形式列在这里…谁先 include 谁独占…报 "Identifier not declared"。**ref 已经踩过一次。**

但 `rtl/ref/filelist.f` **自己没有加**（第 2 段直接从 `fp16_quant.sv` 开始）。

单独跑 `ref` 时不会出问题（`top_ref.sv` 是第一个文件，自己 include 到了）；
但只要哪天把三个 filelist 合起来编（比如做一次三方联合 lint），`ref` 就会因为
守卫被前面的文件抢走而挂掉——而且报错信息完全指不到真因。

**改法**：照抄 varA 那三行，一秒的事。

### P2-3　Q/K/V 装载块没有复位

三个顶层都是：

```systemverilog
always_ff @(posedge clk) begin     // ← 没有 negedge rst_n
  if (ld_en) begin ... end
end
```

`qm/km/vm` 在复位后是 X。功能上没问题（tb 保证先装载再 start），但：
- 综合/形式检查会报"寄存器无复位"的 warning；
- 如果将来做复位后立即 start 的用例（题面的 `reset` 类激励专打这个），会读到 X。

`erow` / `pu` / `om` / `sm` 同样没有复位——但它们都在 start 后被写满才被读，风险低。
`qm/km/vm` 是唯一"可能被未写就读"的，建议至少加复位，或者 tb 里加一条断言。

### P3-1　`QB=10` 这个工作点不是判据推出来的

见 §7 的扫描数据：`qf=4`（等效 7 bit）的 RMSE 就已经是 0.033 < 0.06 判据了。
也就是说**判据允许更小的位宽**，10 bit 是"选"出来的，不是"算"出来的。

这不一定是错——保守选点是合理的。但报告里必须给出选点理由，
否则"为什么不是 8 bit"这个问题无法回答（而 8 bit 还能再省 1,536 个触发器）。

### P3-2　`exp2_unit` 全组合在一拍，是关键路径的主体

`exp2_unit` 内部：常数乘法 → 变量移位 → LUT 查表 → 插值乘加 → 变量移位，
全在 `always_comb` 里，一拍完成。这是 `ref` 9,449 ps 路径的主体。

**改法**：加 1~2 级流水（比如"常数乘法 + 取整"一级、"插值"一级）。
数值结果逐位不变（只是延迟变了），周期数 +1~2/元素。
考虑到 varA/varB 的 softmax 已经是流水结构，加一级几乎不影响总周期。

## 六、关键路径：三方案都卡在同一条链上

| 方案 | 起点 → 终点 | Data Path | Fmax |
|---|---|---|---|
| ref | `cj_reg[2]` → `tsum_reg[20]/D` | **9,449 ps** | ≈ 105.8 MHz |
| varA | `ci_reg[1]` → `om_reg[9][11]/D` | 9,195 ps | ≈ 108.8 MHz |
| varB | `nzrow_r_reg[7]` → `om_reg[9][11]/SI` | 9,195 ps | ≈ 108.8 MHz |

`ref` 这条路径的完整逻辑链（从 timing.rpt 逐点读出来的）：

```
cj → 大扇出 buffer 链 → 读 sm[{ci,cj}]（256:1 mux）
   → sub_117_22（d = maxv − S 的减法器）
   → u_exp/csa_tree_mul_52_71（d × log2e 的乘法树，52 位）
   → u_exp/final_adder_mul_52_71
   → u_exp/csa_tree_attn_rne_shift_52_24:sub_36_9_groupi（RNE 的 36 位减法器）
   → ... → tsum_reg[20]
```

**读法**：整条"取 S → 减 max → 乘 log2e → 移位舍入 → LUT → 插值 → 再移位 → 累加"
全在一拍里完成。这不是周期约束太松，是这条组合链本身就长。

三个推论：

1. **100 MHz 是有效工作点，不是随手选的。** slack=0 表示工具 upsizing 到刚好过，
   周期再紧一点面积就会涨。报告里所有面积数字都必须标注"@100 MHz"。
2. **三方案的 Fmax 几乎一样（106~109 MHz）**，说明提高并行度**没有牺牲频率**——
   因为并行度提高的是"每拍处理几个元素"，而不是"每拍逻辑多深"。这是个好消息，可以写进报告。
3. **`varB` 的终点是 `om_reg/SI`（扫描输入）**，路径被扫描 mux 拖了一截。
   删掉 `om`（§5 P1-1）和换非扫描 DFF（§5 P1-3）会同时改善这条路径。

## 七、精度：位宽扫描数据（我替你跑了一次）

`model/sweep.c` 之前没进 `Makefile`，所以没有留档。我编译跑了一次：

```bash
cd model && gcc -O2 -std=c99 -o /tmp/sweep sweep.c attn_model.c vecgen.c -lm
/tmp/sweep 20260101 4
```

结果（`qb=16` 容器固定，扫 `qf`；判据 RMSE ≤ 0.06 / 最大绝对误差 ≤ 0.20）：

| qf | 等效位宽 | LSB | RMSE(random) | 最大误差 | RMSE(cancel) | 判据余量 | 通过 |
|---|---|---|---|---|---|---|---|
| 4 | 7 | 6.25e-2 | 0.033659 | 0.0905 | 0.033659 | 1.8× | Y |
| 5 | 8 | 3.13e-2 | 0.009508 | 0.0447 | 0.019512 | 6.3× | Y |
| 6 | 9 | 1.56e-2 | 0.004520 | 0.0200 | 0.010602 | 13× | Y |
| **7** | **10** | 7.81e-3 | **0.002118** | 0.0089 | 0.004046 | **28×** | Y |
| 8 | 11 | 3.91e-3 | 0.001217 | 0.0056 | 0.002240 | 49× | Y |
| 10 | 13 | 9.77e-4 | 0.000280 | 0.0012 | 0.000253 | 214× | Y |
| **13** | **16** | 1.22e-4 | **0.000157** | 0.0006 | 0.000174 | 382× | Y |

三条结论：

1. **`varA/varB` 的 10 bit（qf=7）非常安全**：RMSE 0.0021，离判据还有 28 倍余量。
   位宽换成面积这笔交易，在精度上完全站得住——**报告可以理直气壮地写**。
2. **但判据太宽松**：qf=4（7 bit）都能过。所以"选 10 bit"必须给理由
   （比如"留 28× 余量"），而不是"判据逼出来的"。
3. **还能再降**：qf=5（QB=8）的 RMSE 0.0095，余量 6.3 倍，仍很安全，
   可再省 1,536 个触发器（ref 的 2.6%、varB 的 5.6%）。

> ⚠ 这组数字来自 **C 模型**，不是 RTL 仿真。它证明的是"这个位宽的数值精度够"，
> 不证明"RTL 实现了这个模型"。后者必须由 `tb/sys` 的 bit-exact 比对给出。

## 八、按性价比排序的行动清单

| # | 动作 | 预期收益 | 成本 | 风险 |
|---|---|---|---|---|
| 1 | 跑三方案系统级仿真，补 `cycles` / `rmse` | 补上报告最缺的两列 | 每条 ~10 min | 无 |

| 3 | `attn_rne_shift` 常量折叠 | −3% 面积，**Fmax +10~15%** | 加一个宏/参数化 function | 中（要重跑 bit-exact） |
| 4 | `sm` 位宽 32→24 | −3.5% / −4.1% | 改 2 行 | 低（要验极值） |
| 5 | 补 `ref@10bit` 综合 | 修好归因链 | 18 min | 无 |
| 6 | 清掉 `vld_k` 假注释 + 补 ref 的 filelist | 消掉答辩风险 | 2 分钟 | 无 |
| 7 | `exp2` 加流水级 | 换 Fmax | 中 | 中 |
| 8 | QB 10→8 | −2.6% / −5.6% | 重生成向量 + 重跑 | 低（余量 6.3×） |

**如果只做三件事：1 + 2 + 3。**

- 第 2 条让 `varB` 从 208k 降到约 168k，`ref`/`varA` 各省约 4 万；
- 第 3 条再削 3%，同时把 Fmax 从 106 MHz 推到 120 MHz 量级；
- 两条加起来 `varB` ≈ 161k（相对现在 1.29×），**而且数值结果一个 bit 都不变**
  （删的是缓存、改的是移位写法，都不碰运算语义）；
- 第 1 条不省面积，但让报告有数可写——它比前两条更急。

**注意没有"换非扫描触发器"这一条**，原因见 §5 P1-3：那条路是反向优化。

## 九、待确认项（我没能定论的）

1. **`varA` 的双 bank `erow` 会不会在极端调度下饿死 A 级**（静态推演结论：不会，但需波形确认）
   按 B=43 / A=32 / C=16 拍推：row i 占用的 bank 在 row i 的 C 级结束（约 t_i+59）释放，
   而 A 级启动 row i+2 只需在 t_i+82 之前拿到，时间够。
   风险点在 `a2b_v` 是**单寄存器**：若 A 级在 B 级忙时连续完成两行，后一行会覆盖前一行。
   但 bank 只有 2 个，恰好把 A 级限制在"最多领先 2 行"，所以理论上不会丢。
   **这是全设计最难静态证明的一段**，建议专门看一眼波形：`a2b_v` / `bank_busy` / `nfin` 三者。

2. **`recip_unit` 的实际拍数是 43 不是 41**
   `ph=0` 循环 41 拍 + `ph=1` 舍入 1 拍 + `ph=2` 交回 1 拍。
   注释和周期估算都按 41 算，差 2 拍/行 × 16 行 = 32 拍，占 `ref` 总周期的 0.3%。
   不影响任何结论，但报告里的周期式子最好改成 43。

3. **`sweep` 只证明"精度够"，不证明"qb<16 时不会饱和"**
   `sweep.c` 把 `qb` 恒定为 16、只扫 `qf`。所以 §7 的表说明的是
   "该 LSB 下误差多大"，而不是"QB=8 的容器装得下"。
   QB=8/QF=5 的范围是 [-4, 3.97]，题面限 |x| ≤ 2 是安全的；
   但若向量里有 |x| > 3.97（`extreme` 类只到 ±2，应该没有），就会饱和。
   换小 QB 之前先在 `manifest` 里确认没有饱和计数。

4. **`fmax_mhz` 那一列现在是 100（等于约束值），不是实测值**
   `metrics.csv` 里 `fmax_mhz` 填的是 100，这是"约束频率"不是"能达到的频率"。
   真实值要从 §6 的 Data Path 反推（105.8~108.8 MHz）。
   要么改列名为 `clk_constraint_mhz`，要么真做一次频率扫描。

## 附：一句话给答辩用

> 三套实现共享同一份数值契约和同一份数据通路，只在上层编排上不同：
> 参考实现是串行基线，方案 A 用 4-lane 并行加三级流水把延迟压到 1/3，
> 方案 B 再把"全矩阵展开"改成"行融合"，把 256 深的 S/P 缓冲压到 16 深。
>
> 三个方案的面积差异中，约 62% 的部分是触发器阵列——这是一道**存储受限**的题，
> 所以方案 B 的收益主要来自删缓冲而不是删运算单元。
> 比较口径统一在 GPDK045 TT 角、100 MHz、同一份 SDC 与活动率假设下，
> 三方案都能在该频率收敛（Fmax 106~109 MHz）。
