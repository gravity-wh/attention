# 版本与文件管理规范

> 适用：本仓库（数字集成电路设计 · 题目一 Transformer 注意力模块），3~4 人协作。
> 一句话原则：**报告里出现的每一个数字，都必须能被另一个人用「commit + seed + 工艺角」三个坐标重新算出来。**
> 达不到这条的数字，宁可空着。

---

## 1. 先分类，再决定进不进库

版本库里只放「**无法从其他东西重新生成**」的内容。这是唯一判据，比记一堆规则可靠。

| 类别 | 判据 | 例子 | 进库 |
|---|---|---|---|
| **A 源码与配置** | 人写的，无法重算 | `rtl/**/*.sv`、`model/*.c`、`flow/**/*.sh`、`config/*.mk`、`*.tcl` | ✅ 必须 |
| **B 契约与规格** | 人写的，定义"什么算对" | `rtl/common/attn_ports.svh`、`attn_pkg.sv`、`docs/**`、`results/EXPERIMENTS.md` | ✅ 必须 |
| **C 小体积黄金数据** | 机器生成，但重算需要工具链 | `tb/vectors/*/`（smoke 集，约 110 KB/格式） | ✅ 进库 |
| **D 大体积黄金数据** | 同上但很大 | `tb/vectors/*_full/`（9.8 MB） | ❌ 靠 `make vec MODE=full` 重算，seed 进库即可 |
| **E 派生产物** | 跑一次就有，无信息增量 | `runs/**`、`*.log`、`simv`、`netlist.v`、`*.vcd` | ❌ 一律不进 |
| **F 提取后的指标** | 由 E 提炼，体积小、信息密度高 | `results/*.csv`、`results/error_baseline.txt` | ✅ 必须 |

**D 类为什么可以不进库**：它的每一个字节都由 `(seed, qb, qf, lut)` 唯一决定，而这三个数都在 `config/variants.mk` 里、随代码进库。已验证过：跨编译器（gcc 4.8.5 / 15.2）、跨系统（Linux / Windows）重算结果逐字节相同。**这条"可重算"性质本身就是要被验证的资产**，一旦它不成立（例如有人往生成器里塞了 `time()`），D 类就必须改成进库。

**F 类为什么必须进库**：报告表 2/表 3 的每个格子都应当是这里的一行。人眼从 `runs/` 里抄数字，是这份工程最容易出错的一步。

## 2. 目录职责

```
Transform/
├── README.md                 项目入口：现在做到哪、下一步做什么
├── .gitignore / .gitattributes   换行符与产物过滤（见 §8）
├── docs/
│   ├── assignment/           题目原文与需求整理（只读，不改题意）
│   ├── theory/               设计依据：数值格式、综合流程……（会被报告引用）
│   └── engineering/          本文件所在处：流程与协作规范
├── reference/                参考论文（只读）
└── hw/
    ├── Makefile              ★ 唯一入口：不许手敲 vcs / genus
    ├── config/
    │   ├── variants.mk       ★ 方案表 + 每方案数值格式（QB/QF/LUT）
    │   └── pdk.mk            ★ 工艺库/角/约束参数
    ├── rtl/
    │   ├── common/           ★ 三方案共享契约（端口宏、包）
    │   ├── core/             数值件的硬件实现（三方案复用）
    │   ├── ref/ varA/ varB/  各方案的编排逻辑 + filelist.f
    ├── tb/                   测试平台、单元 tb、向量
    ├── model/                黄金模型（C）：向量与自检的唯一来源
    ├── flow/                 sim / synth / collect / power 脚本
    ├── results/              ★ 提取后的指标（进库，报告的原料）
    └── runs/                 一次运行的产物（不进库）
```

带 ★ 的文件/目录是**共享契约**，冲突热点，见 §7。

## 3. TAG 命名：把实验条件写进名字里

`runs/<TAG>/` 是每次运行的落脚点，`results/metrics.csv` 的每一行也以 TAG 为键。命名规则：

```
<variant>-<优化点>-<关键参数>[-<corner>]
```

| 例子 | 含义 |
|---|---|
| `ref-syn-tt` | 参考实现在 tt 角的综合 |
| `varA-ke8-w8-tt` | 方案 A，KE 并行度 8、宽 8 位，tt 角 |
| `varA-ke4-w8-ss` | 同一方案改并行度 4，ss 角（单变量对照的另一半） |

规则：
1. **同一 TAG 只跑一次**。想改参数就换 TAG，不要覆盖 —— 覆盖掉的正是对照组。
2. 参数必须写进名字，不能只写在脑子里。表 3 是"单变量对照"，对照成立的前提是两个 TAG 只差一个词。
3. 角必须出现在名字里或由 `make` 追加（`synall` 会自动加 `-tt/-ss/-ff`）。

## 4. 提交规范

### 4.1 一次提交只做一件事

判断标准：**能不能用一句话说清，且这句话里没有"顺便"**。

好：`fix(syn): filelist 清洗误删 attn_math.svh，导致 Genus 报 Unresolved subprogram`
坏：`修一堆问题`

### 4.2 消息格式（Conventional Commits 的一个小子集）

```
<type>(<scope>): <做了什么，不超过 60 字>

<为什么这么做。踩过的坑写清楚，比"改了什么"值钱得多。>
```

| type | 用于 |
|---|---|
| `feat` | 新增能力（新方案、新目标、新脚本） |
| `fix` | 修正错误（含流程 bug） |
| `refactor` | 不改行为的结构调整 |
| `docs` | 文档 |
| `chore` | 配置、忽略规则、依赖 |
| `exp` | **实验性提交**：跑了一组对照、数据进 `results/`，代码不一定最终采用 |

`scope` 用目录名：`rtl` / `model` / `sim` / `syn` / `collect` / `num`（数值格式）/ `docs`。

### 4.3 什么改动必须"成套"提交

这几组是**同一件事的多个面**，拆开提交会让仓库短暂处于"验证过的和要跑的不是同一份"的状态：

| 改了 | 必须同一提交里同时改 |
|---|---|
| `QB/QF/LUT`（`config/variants.mk`） | 重跑 `make vec VARIANT=<v>`（黄金值换文件名）＋ RTL 的 `` `define `` 传参 ＋ `results/error_baseline.txt` |
| `model/attn_model.c` 的数值行为 | 重跑 `make vec` 与 `make err`，两个产物一起提交 |
| `rtl/core/**` 或 `rtl/common/**` | 重跑 `make regress`（六个方案受影响时 `make unitall`） |
| `flow/synth/**` 或 `config/pdk.mk` | 重跑 `make syn`，`results/metrics.csv` 一起更新 |
| `attn_ports.svh`（端口契约） | 三个 `top_*.sv` ＋ `tb_attn.sv` ＋ 三个 `filelist.f` |

> 允许"只改一处"的例外只有一个：先提交 `docs` 里的设计说明，再提交实现。文档先行比代码先行安全。

### 4.4 提交前必过

```bash
cd hw && make preflight
```

它检查的是"**这次提交有没有让仓库处于自相矛盾的状态**"：格式三处是否同源、向量是否与模型一致、工作区是否真的只有想提交的东西。详见 §9。

## 5. 分支与协作（4 人）

### 5.1 主线 + 短分支

```
main ──●──●──────●────────●──●──▶   （永远可跑：make modeltest / vecfsck 全绿）
        \        /  \      /
         feat/varA   fix/syn-filelist
```

- **禁止长期分支**。方案 A 和方案 B 不是两个分支，而是 `rtl/varA/`、`rtl/varB/` 两个目录 —— 目录隔离比分支隔离更适合"三套实现要长期并存互相比对"这种结构。
- 分支存活期 ≤ 3 天。超过说明任务切得太大。
- 合并前必须 `make preflight` + 对应层面的回归（改 RTL 跑 `make regress`，改流程跑 `make flowtest`）。

### 5.2 四人分工与最小冲突面

| 角色 | 主要写 | 只读（改了要通知） |
|---|---|---|
| A 数据通路 RTL | `rtl/varA/**` | `rtl/common/**`、`rtl/core/**` |
| B 数值/Softmax | `rtl/core/**`、`model/**` | `rtl/common/attn_pkg.sv` |
| C 验证 | `tb/**`、`flow/sim/**`、`tb/vectors` 生成 | `rtl/common/attn_ports.svh` |
| D 综合/汇报 | `flow/synth/**`、`flow/collect/**`、`config/pdk.mk`、`docs/**`、`results/**` | 全部 |

这样切的依据是**文件不重叠**，不是"任务看起来均匀"。`rtl/core/` 只有 B 写，`flow/synth/` 只有 D 写，`rtl/varA/` 只有 A 写 —— 三个人同时提交也不会冲突。

### 5.3 共享契约文件（必须走"公告-修改"流程）

下面这几个文件，**改之前先在群里说一句**，改完立刻提交（不要攒着）：

- `rtl/common/attn_ports.svh` —— 端口契约，改一个端口三家全挂
- `rtl/common/attn_pkg.sv` —— 数值常量（S_FRAC/P_FRAC/RECIP_SH…），改一个三套数值全变
- `config/variants.mk` —— 每方案的 QB/QF/LUT
- `config/pdk.mk` —— 工艺库、角、约束参数（面积/功耗数字全由它决定）
- `hw/Makefile` —— 流程入口

判断方法：**这个文件被两个以上方案的 filelist 直接或间接引用了吗？** 是 → 契约文件。

### 5.4 共用一台机器时，任务必须串行

仿真和综合都在同一台 CentOS 虚拟机上跑，镜像里只有**一份** `/root/work/hw`。所以：

- **同一时刻只允许一个 VM 任务**。每个调用开头的 `rm -rf /root/work/hw` 会删掉别人正在用的编译目录，两路并发互相抹的结果就是「编译日志凭空消失」「runs/ 建到别处」，极难排查。
- **不要用 flock 排队**：实测被中断（超时/中断）的实例会把锁留在原地，后续调用全部跟着卡死，比并发本身更难查。`runvm.sh` 现在的做法是「每轮独立日志文件名 + 开头按进程名 pkill 残留 + 取回后校验轮次标记」—— 即使两路同时进来，各自取回的也是自己的日志，不会互相冒充，最坏情况也只是这轮白跑，不会拖住下一轮。
- 所以串行靠**人**，不靠锁：同一时间只发起一个长任务，发起前 `ps -eo pid,etimes,cmd` 看一眼客户机是否空闲。
- 长任务（综合尤其）**用独立工作目录和独立日志**：`/root/syn_work/hw` + `/mnt/hgfs/share/_syn/syn.log`，不要挤在所有人共用的 `/root/work/hw` 里。
- 排查「任务到底在跑还是被杀」时，看 **`ps -eo pid,etimes,cmd`**，不要看日志文件在不在 —— 日志可能还没被 `tee` 刷出来，也可能被上一轮覆盖。日志是证据，进程状态才是事实。

## 6. 快照与标签

`main` 上的每个提交都能跑，但不是每个提交都值得引用。**只有下面三种情况打 tag**：

| 时机 | tag 形式 | 为什么 |
|---|---|---|
| 一组完整对照数据出炉（六类 PASS + 综合数据齐） | `exp-<date>-<简述>`，如 `exp-20261105-ke8` | 报告表 2 引用的就是它 |
| 提交材料冻结 | `submit-v1` | 答辩/交作业的对应版本 |
| 数值格式定版 | `num-qb10qf7` | 别人引用"10 bit 方案"时指的是它 |

报告里引用数字时写 `commit fb80f87 / tag exp-20261105-ke8 / seed 20260101 / TT_25C_1V20`。四个坐标缺一不可 —— 少了 seed 无法复现数据，少了角无法复现综合。

`make manifest` 每次运行都会把 commit、seed、clock、PVT、hostname 写进 `runs/<TAG>/INFO.txt`；`make collect` 再把它搬进 `results/metrics.csv`。**这是唯一允许进入报告的数字来源通道。**

## 7. 大文件政策

当前仓库 3.4 MB，最大的文件是 1.4 MB 的参考论文 PDF。**不需要 Git LFS**，但需要红线：

| 阈值 | 处理 |
|---|---|
| < 2 MB | 正常进库 |
| 2 ~ 20 MB | 仅限 PDF/图片/数据表；一年内总数不超过 20 个；否则改用 LFS |
| > 20 MB | **不进库**。放 NAS 共享目录，库里只存一条 `reference/SOURCES.md` 记录路径与哈希 |

明确不进库的：`*.gds` / `*.def` / `*.spef` / `*.vcd` / `*.fsdb` / 网表 / 综合数据库。这些都是"跑一次就有"，且体积与信息量不成比例。

> 现状提醒：两个参考论文的文件名是从数据库直接导出后被截断的 ——
> `reference/A 28nm 27.5TOPS_W Approximate-Computing-...pdf`（1.45 MB）、
> `reference/A_28nm_15.59J_Token_Full-Digital_...pdf`（1.25 MB），
> 开头的 `A ` 是被切掉的首作者，中间还夹了空格。这类文件比大文件更麻烦：
> 半年后没人知道它是什么，检索也搜不到。
> 建议改成 `reference/<第一作者姓氏><年份>-<短主题>.pdf`，例如
> `reference/wang2021-27.5tops-approx-attn.pdf`；
> 改名时同时补一份 `reference/SOURCES.md`（DOI/链接 + sha256 + 一句话说明），
> 这样即使文件名再被谁改乱，也能凭哈希认回来。

## 8. `.gitignore` / `.gitattributes` 的边界

两份文件的职责不同，不要混用：

- **`.gitignore`** 决定"哪些文件压根不跟踪"。
- **`.gitattributes`** 决定"跟踪的文件在磁盘上用什么换行符、是不是二进制"。

换行符这块本项目已经踩过：仓库在 Windows 上编辑、在 Linux 上跑，`.sh` 一旦提交成 CRLF，Linux 上直接 `bad interpreter: /bin/bash^M`。所以 `.gitattributes` 里 `*.sh`、`Makefile`、`*.f`、`*.sv` 全部强制 `eol=lf`。

**关键认知**：`.gitattributes` 只规范化**提交内容**，管不了**磁盘上的字节**。程序写文件时必须自己保证字节一致（本项目的 `dumpvec` 用 `fopen(...,"wb")` 就是这个原因）。判断可复现性不能看 `git status` 干不干净，要看 `git diff --name-only HEAD` 加逐字节比对。

## 9. 提交前自检：`make preflight`

一条命令检查"仓库有没有自相矛盾"：

```
cd hw && make preflight
```

检查项与失败含义：

| 检查 | 失败说明 |
|---|---|
| 真实变更集（`git diff --name-only HEAD`） | 有未提交改动 —— 现在跑的数据绑不到 commit |
| 数值格式三处同源 | `variants.mk` 的 QB/QF/LUT 与向量文件名、RTL 宏对不上 |
| 向量回读校验（`make vecfsck`） | 改了模型没重生成向量，或文件被截断 |
| 模型自检（`make modeltest`） | 数值原语坏了，后面所有 RTL 都在翻译错误的规格 |
| 未跟踪的可疑文件 | 有 `.exe`/`.log`/`.vcd` 之类的派生物混进来了 |
| PDK 一致性 | `config/pdk.mk` 里角与库路径对不上（只在 VM 上能查文件是否存在） |

> **NAS 上的已知假阳性**：本仓库放在 SMB 共享盘上，`git status` 会把一批没改过的 `*.hex` 报成 ` M`（索引 stat 缓存刷新不掉）。判断真实改动**只能**用
> `git diff --name-only HEAD`，`git status --porcelain` 在这个仓库里不可信。

## 10. 本项目真实踩过的坑（都值得写进报告"工程实践"一节）

| 事故 | 表现 | 根因 | 现在的防线 |
|---|---|---|---|
| 编译产物进库 | `attn_*.exe` 被 `git add` | 用 `git add -A` 不看内容 | `.gitignore` 加 `*.exe`；`preflight` 检查 |
| 黄金值互相覆盖 | ref(16bit) 的 `exp.hex` 被 varA(10bit) 覆盖，tb 报"逐位全错" | 一个种子目录只有一份 `exp.hex` | 文件名带格式标签 `_exp_qb10qf7.hex` |
| 参考值跨编译器漂移 | 同一 seed 在 Linux/Windows 生成的 `ref.hex` 差 1~2 ULP | 用了 libm 的 `exp()`；FMA 收缩 | 自写确定性 exp + `-ffp-contract=off` |
| 行尾悄悄不同 | 磁盘 CRLF、仓库 LF，`git status` 却干净 | `fopen(...,"w")` 在 Windows 转 CRLF | `fopen(...,"wb")` |
| 清单被覆盖 | 生成 varA 时 ref 的 Σp 体检结果消失 | 清单只有一个文件名，但内容依赖格式 | `manifest_<cfg>.txt` |
| 头文件守卫跨文件生效 | Genus 报几十条 `Unresolved subprogram reference`，仿真却是好的 | `attn_math.svh` 带 `ifndef` 守卫，但设计上要"每模块私有副本"；VCS 按文件独立编译单元才侥幸通过 | `attn_math.svh` 以**设计文件**身份进 filelist，编译一次成 `$unit` 作用域 |
| 脚本自杀 | `runvm.sh` 连 `echo` 都跑不到就返回旧日志 | `pkill -f simv` 的模式串出现在执行它的进程自己的命令行里 | 用 `[s]imv` 方括号技巧；或整条命令 base64 后执行 |
| 别人的清理杀掉我的仿真 | 六类里随机两类日志是空的、结果 FAIL，重跑又好 | 另一条跑道的 `pkill -f simv` 命中了同一个可执行文件（VCS 因 ASLR 还会 re-exec 一次，正好在重启瞬间被打中） | 仿真器可改名：`SIMV_NAME=attn_sim_iso make regress`；见 §5.4 |
| 综合取数接口不存在 | 跑满 17 分钟，最后 metrics 里面积/时序/功耗全是 MISSING | Genus 15.20 没有 `get_attribute [get_designs X] area`、`get_timing_paths` | 取值主渠道改为解析报告文本，单位从报告里读（`timing/qor` 是 ps、`power` 是 nW） |
| 演示库面积全为 0 | 综合面积报 0，`A₀/A` 变成无穷 | GPDK045/gsclib045 的 `.lib` 里 `area : 0.0` | 强制 `read_physical -lef`，面积取自 LEF；面积为 0 直接 fail |

这份表的价值在报告里叫"**可复现性与工程严谨性**"—— 题目给的 10 分复现分，考的就是你有没有这套东西。

## 11. 命令速查

```bash
# 日常
cd hw
make preflight                    # 提交前必过
make modeltest && make vecfsck    # 数值层两道闸
make sim VARIANT=varA CAT=random  # 单类激励调试
make regress VARIANT=varA MODE=smoke   # 六类回归

# 综合与汇总（在 VM 上，见 docs/theory/02）
make syn VARIANT=ref TAG=ref-syn-tt
make synall VARIANT=varA TAG=varA-ke8
make collect && make table        # runs/ → results/metrics.csv → results/tables.md

# 版本
git diff --name-only HEAD         # ★ 唯一可信的"改了什么"（NAS 上 git status 会骗人）
git add -p                        # 逐块确认，别用 git add -A
git commit -m "fix(syn): ..."     # 一条一件事
git tag exp-20261105-ke8          # 数据出炉才打
```

## 12. 一页纸总结

1. **只放无法重算的东西**，其余靠 `seed + 脚本` 重算。
2. **数字必须有四个坐标**：commit、seed、工艺角、TAG。
3. **一次提交一件事**，改契约要成套改、成套提交。
4. **契约文件先公告后修改**（端口头、数值常量、`config/*.mk`、`Makefile`）。
5. **分支短、目录分**；方案 A/B 是目录，不是分支。
6. **判断真实改动只看 `git diff --name-only HEAD`**，这个仓库在 NAS 上。
7. 报错的坑写进提交信息和本文件 §10，**下一个人才不会重踩**。
