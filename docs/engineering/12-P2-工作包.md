## 0. 任务一句话

把 `varB` 的 1,738 拍讲清楚，并只在一个可证伪的假设下改 RTL：`erow` bank 生命周期 + B→C 反压。

当前 `varB` 的 1,738 拍不是文件头写的 `max(80,41,80)=80 拍/行`。按代码里的 bank 占用：

- A 启动时占 bank（`top_varB.sv:258-268`）；
- bank 到 C 级 P·V 结束才释放（`:357-365`）；
- 单 bank 占用 ≈ A(80) + B(43) + C(80/96)；
- 2 个 bank 的吞吐下限 ≈ 101.5~109.5 拍/行；
- 16 行 ≈ 1,608~1,752 拍，实测 1,738 拍。

**先测，不要先改。**

## 2. 第一张纸：1,738 拍预算

不改 RTL，先用现有 `varB` 仿真/波形填下表：

| 项 | 符号/条件 | 实测 | 备注 |
|---|---|---:|---|
| A 级：QK 64 + exp 16 | `a_busy` | 80 | 每行 |
| B 级：倒数 + 握手 | `rcp_busy` / `b_busy` | 43~44 | 每行 |
| C 级：归一 16 + P·V | `c_busy` | 80 或 96 | 关键未知 |
| bank 等待 | `bank_busy` 满 | ? | 2 bank 的限制 |
| B→C 等待 | `b2c_v` | ? | 单寄存器 |
| 填充/排空 | 首行/末行 | ? | |
| **总计** | `done` | **1,738** | 与表一致 |

### 2.1 第一张纸已经预填（控制级逐拍模型，不是波形）

`hw/flow/collect/cycle_model.py` 能复现三方案拍数（diff 全 0），其中 varB 的分解是：

| 项 | 拍数 | 说明 |
|---|---:|---|
| A 级每行 | 81 | 占 bank 1 拍 + QK 64 + exp 16 |
| B 级每行 | 45 | 拉 `div_start` 1 + 长除 41 + RNE 1 + 交回 1 |
| C 级每行 | **80** | 归一 16 + P·V 4 组 × 16；**不存在 96**（PV 最多 4 组，只会因跳零组变少） |
| 行间隔 | 81 / 126 交替 | 奇数行 81，偶数行多等 45 拍 bank |
| 前导 | 82 | 首行 A 启动到首行 C 开始 |
| **bank 等待合计** | **360** | 8 行 × 45 拍 —— 这就是原表里那个"?" |
| 总计 | 1,738 | 82 + 8×81 + 8×126 |

结论与 §3.1 一致：**bank 等待是主项**，可以进第二张纸。单 bank 占用按 C=80 算是
1 + 81 + 45 + 80 = **206 拍**；改成"归一末释放"后是 1 + 81 + 45 + 16 = **142 拍**。
两种占用 / 2 个 bank 分别给出 103 和 71 拍/行的吞吐上限，前者被 A 的 81 拍卡住时才开始排队——
这就是 81/126 交替的来历。§3.1 的目标拍数已用同一模型复核为 **1,423 拍**。

验收：各项之和与 1,738 差 ≤2 拍；若对不上，先查 C 级是否 96 拍，而不是先改 bank。

建议观测（tb 层级引用，不改 RTL）：

```systemverilog
$display("a=%0d b=%0d c=%0d bank=%b b2c=%b nfin=%0d",
         dut.a_busy, dut.b_busy, dut.c_busy, dut.bank_busy,
         dut.b2c_v, dut.nfin);
```

> 若 P3 不同意在 tb 加打印，就在 Verdi 里看 `bank_busy/a_busy/b_busy/c_busy/b2c_v`，把每行时间戳抄进表。

## 3. 第二张纸：bank + B→C 反压实验

只有第一张纸证明“bank 等待是主项”后，才做这个补丁。

### 3.1 假设

把 bank 释放从 P·V 结束提前到 normalize 结束（最后一个 `erow` 读之后），单行 bank 占用
从 **206** 拍（1 占位 + A 81 + B 45 + C 80）降到 **142** 拍（1 + 81 + 45 + 归一 16）；
2 bank 吞吐从 103 拍/行降到 71 拍/行，A 级 81 拍/行成为瓶颈，总周期 **1,423 拍**。

> 这个数先由 `hw/flow/collect/cycle_model.py --study` 逐拍复核（原估 1,421，差 2 拍在首行前导），
> 2026-11-14 再由 VCS 实测确认：616 例 `mism 0`、`lat 1423`（见 §3.4）。
> 补丁在 `docs/engineering/patches/12-varB-early-release.diff`，只挪两行、不加逻辑，**已合入主干**。

### 3.2 反压：不是达标条件，是保险

**只改释放点就能拿到 1,423 拍**——A 级 81 拍/行、C 级 80 拍/行，那 1 拍余量足够
`b2c_v` 在下一拍必被消费，B 不会撞上"结果还没取走"。模型跑的四种配置
（2/3 bank × 释放点）里，加不加 B→C 反压都是 1,423。

但余量**只有 1 拍**，而且设计里没有任何断言。所以建议在拿到 1,423 之后再加反压，
把它变成"改坏了会挂死"而不是"改坏了静默丢一行"：

B→C 只有单寄存器 `b2c_v`；B 完成时若 C 还没消费，会覆盖结果。加反压的写法：

```systemverilog
// B 级完成前检查 b2c_v，保证 1-deep FIFO
if (!b_busy) begin
  if (a2b_v && !b2c_v) begin ... end
end else if (rcp_done) begin
  if (!b2c_v) begin
    b2c_v <= 1;
    ...
  end
end
```

具体写法以现有 `top_varB.sv:305-320` 为准。

> **反压这一版自己有两个坑**（踩了会挂死而不是变快）：
> 1. `recip_unit` 的 `done` 是**单拍脉冲**，`r_out` 才是保持的。上面那个 `if (!b2c_v)`
>    一旦跳过，`done` 已经过去，B 会永久等下一个 `rcp_done`。必须把"算完了但没送出去"
>    锁存成 `b_done_q`，条件写成 `else if (rcp_done || b_done_q)`。
> 2. 只在 B 侧加反压不够：B 阻塞时 `a2b_v` 仍是单寄存器，A 每 81 拍产出一行仍会覆盖它。
>    A 取 bank 前要加 `&& !a2b_v`（或把 `a2b_v` 升级成带 full 标志的 1 深 FIFO）。

> 为什么值得补：余量只有 1 拍，而**设计里没有任何断言**。将来谁把 C 级改成 81 拍，
> 表现是静默丢一行（`nfin` 卡在 15、`done` 永不拉高）而不是报错。
> 加反压之外，`assert (b2c_v |-> ##[1:2] !b2c_v)` 这类检查更划算。

### 3.3 验收

`lat_min` 与 `lat_max` 必须相等；不等说明 `done` 时序变了，是另一个 bug。

拍数不对时的定位表：

| 实测 | mismatch | 含义 |

### 3.4 实测结果（2026-11-14，已合入主干）

在 CentOS 7.9 VM（VCS V-2023.12-SP2，Genus 15.20，SC9MC tt/ss/ff）上跑完，**预测与实测完全一致**：

| 项 | 结果 | 与预测 |
|---|---|---|
| smoke 12 例 | 六类 PASS，`lat 1423` | ✓ |
| full 616 例 | 六类 PASS，`mism 0`，`lat_min/avg/max = 1423/1423/1423` | ✓ |
| 精度 | worst RMSE 0.002492、max\|e\| 0.006034 | 与原实现逐字段相同 ✓ |
| tt 综合 | 73,296.9 µm² / 27,069 cell / 16.096 mW / WNS 0 | 面积 +0.62%、功耗 +0.45% |
| ss 综合 | 83,004.8 µm² / 31,554 cell / 14.806 mW / WNS 0 | 面积 −0.51%、功耗 −0.88% |
| ff 综合 | 67,074.6 µm² / 23,437 cell / 18.463 mW / WNS +0.001 | 面积 +0.01%、功耗 +0.03% |

**结论：花 453 µm²（tt，+0.62%）换 315 拍**——纯计算口径 −18.1%（1,738 → 1,423），
端到端口径 −12.6%（2,506 → 2,191），**零新增寄存器**。
三个角的面积/功耗变化都在 ±0.9% 内、方向不一致，属于映射噪声级——说明这条改动的资源代价基本为零，
收益全部来自调度。

`cancel` 类的 1375 / 1399 / 1423 三档是跳过零组的既有特性（原实现同样如此），不是本次改动引入。

## 4. 第三张纸：装载边界

题面要求“从开始装载到结果全部输出计时”。改口径前 `tb_attn.sv` 先装载 768 拍再发 `start`，`lat` 不含装载；**2026-11-14 已按方案 A 改掉，见下方决议**。

P2 不在顶层加端口；先与 P4 约定：

- 方案 A：P4 在 tb/collect 里把 768 拍加到 `cycles`；
- 方案 B：P2 在顶层加 `S_LOAD`/`busy`，从第一个 `ld_en` 起算；这会改端口语义，必须 P3/P4 同意。

**默认走方案 A**，因为不改 RTL、不破坏三方案端口契约。

> **决议（2026-11-14 22:40 执行，方案 A）**：`cycles` 改为**端到端含装载**，
> 与题面“从开始装载到结果全部输出计时”一致。落地方式按方案 A 的最小侵入版本：
>
> 1. `tb_attn.sv` 的 `drive_load()` 返回自己花掉的拍数，主流程取最坏值，
>    在 `[SUMMARY]` 行末尾加 `ld=`——**实测，不硬编码 768**；
> 2. `flow/sim/run.sh` 把 `ld` 写进 `summary.csv` 第 14 列；
> 3. `flow/collect/collect.py` 令 `cycles = lat_max + ld`，同时新增 `cycles_calc`
>    列保留 `start`→`done` 的原值，供 `cycle_model.py` 对账。
>
> **RTL 与端口一字未动**：方案 B 需要的 `S_LOAD`/`busy` 端口语义变更不做，
> P3/P4 的契约不变。代价是三方案的 D/E 全部重算（ref 10,433 / varA 3,623 /
> varB 2,506 拍，D₀/D 4.16×、E₀/E 10.53×），已同步进 `05` §5 与两张结果表。
