# RTL 优化阶段的任务划分与协作边界

> 场景：MAC（QK·Kᵀ 与 P·V 的乘加）已交给一人，Softmax 交给一人，问"其余的流程还能切出什么单元"。
> 结论：**再切两个就够——"编排与存储"和"验证与测量"。但切之前必须先做一次 0.5 天的重构，否则前两个人一定撞在同一个文件里。**

---

## 一、先说你现在的切法有哪些隐患

按"算法块"切人是最自然的分法，也是最容易返工的分法。这个仓库里具体的冲突点有四个，全部有据可查：

### 1.1 算术写在顶层里，两个人只能改同一个文件

```
top_varA.sv:144  assign qk_p[0] = qm[...] * km[...];      ← MAC
top_varA.sv:185  assign pv_p[0] = pu[...] * vm[...];      ← MAC
top_varA.sv:120  exp2_unit u_exp (...);                   ← Softmax
top_varA.sv:201  assign pr_c = erow[...] * c_rval;        ← Softmax（归一化乘）
top_varB.sv:145 / 187 / 120                                ← 同样的四段
```

**同一个 `top_*.sv` 里，MAC 的 8 行 `assign` 和 softmax 的实例化、乘法器、状态机交织在一起。**
两个人各开一个分支改同一个文件，合并时是逐行冲突，而且冲突出现在**状态机**里——
最不该由两个人同时碰的地方。

### 1.2 共享的"数值契约"是单例，谁改谁阻塞别人

| 文件 | 为什么是单例 |
|---|---|
| `rtl/common/attn_pkg.sv` | `S_FRAC / P_FRAC / Q_BITS / EXP_LUT_BITS` 全工程唯一真源 |
| `hw/config/variants.mk` | `qb/qf/lut` 三个值决定向量文件名的标签 |
| `hw/model/attn_model.c` | "逐位一致"的比对对象 |
| `tb/vectors/s*/` | 由模型导出，格式一改全部作废 |

只要有一方动了 `attn_pkg`，另一方的六类回归立刻全红，而**红的原因不在他自己的代码里**。
这是团队协作里最难排查的一类故障：「我什么都没改，怎么就挂了」。

### 1.3 关键路径是共享资源，Fmax 收益无法归因

三个方案的 9 449~9 451 ps 都穿过同一条链（`d=max−S → ×log2e → LUT → 插值 → tsum`）。
MAC 的人改加树、softmax 的人改 exp，都会让这条路径变短——**合并之后报出来的 Fmax 是谁的功劳？**
报告里必须能回答，否则"结构或参数优化"那 20 分拿不稳。

### 1.4 我上一份文档里的头号建议，正好横跨这两人的边界

`09-Softmax优化空间.md` §4.1 的「把 log2e 折进 K 的量化」：
**改的是 K 的量化（MAC 端的输入），省的是 exp 的乘树（softmax 端的逻辑）。**
不先定归属，这条最值钱的改动会在两人之间来回踢。

## 二、建议的四个任务单元

切分原则一句话：**不是"谁写哪个模块"，而是"谁能独立交出一组单变量对照"**。
20 分给"对照实验与结果解释"，40 分给"相对参考实现的改善"——**交不出对照的单元，等于没做**。

| 单元 | 范围 | 独占文件 | 交付的对照（表 3 的一行） | 估算 |
|---|---|---|---|---|
| **U1 MAC** | QK 点积、P·V 加权求和：lane 数、加树结构、稀疏跳过、部分积压缩 | `rtl/core/qk_dot4.sv`、`pv_dot4.sv`（**需新建**）、`sparse_gate.sv` | lane 1→4；稀疏跳过开/关 | 5~7 天 |
| **U2 Softmax** | exp 近似、倒数、归一化方式、exp 排布 | `rtl/core/exp2_unit.sv`、`recip_unit.sv`、`norm_unit.sv`（**需新建**） | LUT 段数；log2e 折进 K；除法 41→4 拍 | 5~7 天 |
| **U3 编排与存储** | 三级流水、行融合、双缓冲、输出流式、状态机、端口协议 | `rtl/{ref,varA,varB}/top_*.sv`、`attn_ports.svh` | 全展开 vs 行融合（已在）；exp/norm 隐藏开/关 | 5~7 天 |
| **U4 验证与测量** | tb、向量、覆盖率、bit-exact、综合/功耗/PR、指标汇总 | `tb/**`、`flow/**`、`model/**`、`attn_pkg.sv`、`variants.mk` | **不产出对照，产出全部证据链** | 全程 |

### 为什么是这四个，而不是再拆细

- **U3 必须独立**：它是唯一同时动 `top_*.sv` 状态机的人。如果让 U1 或 U2 兼，等于让一个人同时改算术和调度，
  一旦时序不对，无法判断是算错了还是排错了。
- **U4 必须独立且"有权说不"**：谁跑回归，谁就有权拒绝合并。合并权与开发权分开，是这题唯一能保住
  "逐位一致"的组织手段——因为这个判据一旦破了，前面所有数据全部作废。
- **不要再拆出"物理实现"单元**：`flow/pnr` 已经跑通（07 文档），PR 是流程活不是设计活，
  挂在 U4 下面更省沟通成本。

### 3 人怎么分（如果凑不齐 4 人）

| 方案 | 分配 | 风险 |
|---|---|---|
| 推荐 | A=U1，B=U2，C=U3+U4 | C 负载重，但接口最少；适合 C 是熟流程的人 |
| 备选 | A=U1+U3，B=U2，C=U4 | 少一次交接，但 A 要同时改算术和状态机 |
| 不建议 | A=U1，B=U2+U3，C=U4 | softmax 的排布改动必然要动状态机，B 会变成两个人的活 |

## 三、切人之前先做一次 0.5 天的重构

**目的：让 U1 有自己的文件。** 目前 8 行乘加写在两个顶层里，不抽出来，文件边界就不存在。

```verilog
// rtl/core/qk_dot4.sv —— 4 lane 点积，纯组合，无状态
module qk_dot4 #(parameter int QB = 10) (
  input  logic signed [QB-1:0] a0, a1, a2, a3,   // 行向量 4 个元素
  input  logic signed [QB-1:0] b0, b1, b2, b3,   // 列向量 4 个元素
  output logic signed [2*QB+1:0] sum             // 部分和（不累加）
);
  logic signed [2*QB-1:0] p0, p1, p2, p3;
  assign p0 = a0 * b0;  ...  assign sum = (p0 + p1) + (p2 + p3);
endmodule
```

三件事必须同时做，否则重构本身会引入不一致：

1. 顶层改成实例化，`qk_sum` 的位宽与语义**逐位不变**；
2. `make regress VARIANT=varA/varB` 六类全过、`mism=0`（证明重构没改数值）；
3. 提交信息写清"纯结构重构，数值不变"，并把 `runs/` 里的前后周期数贴进 commit。

> 这次重构的收益不是性能，是**让后面三个人的分支互不重叠**。0.5 天买 3 周不打架，很划算。

## 七、成对测量：已落地的改动（2026-11-10）

### 7.1 根因不是"tag 不同"，是"半行冒充整行"

`collect.py` 原来这一行：

```python
"status": sim.get("status", "SYN-ONLY"),
```

只要 `summary.csv` 存在就写 `PASS`，**哪怕一行综合数据都没有**。于是那四行看起来
"功能通过、精度达标"，只有 `E` 是空的——而空值在表里和在报告里都最容易被漏掉。
雪上加霜的是 `clk` 也只从 `syn/metrics.csv` 取，没跑综合连 `D` 都算不出来。

所以修的不是"让 tag 一样"，是**让不完整的行不许冒充完整的行**。

`rtl.bak-20261030-105430/` 仍留在 VM 上，作为"改动前"的对照。

根因是**同步是单向的**（NAS → VM），VM 上改完没有回写。这次没被覆盖纯属侥幸——
10-30 之后没再跑过 `sync_from_nas.bat`。以后要么所有 RTL 改动都在 NAS 侧做，
要么改完立刻 `scp` 回来。

### 7.6 同一个根因的三个副作用

1. **VM 的 `config/` 落后**：`PDK` 默认还是 `GPDK045`，`pdk.mk` 里连 SC9MC 的库路径都没有。
   在 VM 上 `make syn` 出来的是 45 nm，而 NAS 认为默认是 40 nm —— 表里混角的隐患。
2. **VM 的 `flow/synth/syn.tcl` 落后**：它是 10-30 的老版本，无条件 `read_physical -lef`，
   而 SC9MC 的 LEF 是 macro-only、没有 tech LEF，于是第一次 `make pair` 直接报
   `PHYS-10: Specify the tech LEF first`（1 分 17 秒挂掉）。把 NAS 的新版 `syn.tcl`
   `run_syn.sh` 同步过去后正常。
3. **`make table` 生成的表 3 还只是表 2 的镜像**，没有按"调整前/调整后"两列排。
   现在 `-base`/`-opt` 成对存在了，改 `make_table.py` 就能出真正的单变量对照表——
   这是 U4 的下一条待办，不是数据问题。

### 7.7 重跑时新踩的两个坑（写进交接文档，别再踩一次）

**坑一：VCS 会挂在向外回连上，看起来像"编译巨慢"。**

```
ps: vcs1   %CPU 0.3   TIME 00:00:02   ELAPSED 12:33
ss: ESTAB  192.168.85.130:41658 → 198.182.50.26:80
```

`vcs1` 编译 `varA` 时向 Synopsys 的服务器（198.182.50.26:80）建了连接，
校园网/代理环境下连上但收不到响应，进程停在 `futex_wait_queue_me`，
**12 分钟只用掉 2 秒 CPU**。误判成"网表更大所以更慢"会白等一小时。

处置：`ip route add blackhole 198.182.50.26/32`，之后连接立即失败，编译恢复正常。
判断口诀：**看 CPU 时间，不看墙钟** —— 墙钟 12 分钟而 CPU 2 秒，一定是阻塞，不是计算。

**坑二：向量必须按数值格式逐份检查，只看目录会漏。**

`genvec` 的产物带格式标签：`_exp_qb16qf13.hex`（ref）与 `_exp_qb10qf7.hex`（varA/varB）是两套文件，
清单分别是 `geninfo_<cfg>.txt`。旧 `regress.sh` 只判断 `tb/vectors/s<seed>_full/` 目录是否存在，
于是 `pairall` 里先跑的 ref 把目录建出来之后，**varA 的六类激励全部 FAIL，报"向量打不开"**——
看起来像 RTL 崩了，实际是流程漏判。

已修：检查 `geninfo_${CFGTAG}.txt` 是否存在，并把 `build.sh` 挪到检查之后
（先确认黄金值在，再花 1 分钟编 simv）。这条修改同时说明一件事：
**`pairall` 这种"一条命令跑三个方案"的封装，必须自己验证每个方案的前置条件，
不能假设"上一个方案跑通了，这个也能跑"。**
